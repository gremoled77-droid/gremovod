# Проверка изменения

## 1. Выбрать проверки по типу изменения

| Изменение | Команда | Откуда |
|---|---|---|
| `backend/**`, `db/**` | `python -m pytest backend` | корень репозитория, venv проекта |
| `backend/**` (без pytest) | `python -X utf8 -m unittest discover -s backend -p "test_*.py"` | корень репозитория |
| `frontend/**` | `npm test` и `npm run build` | `frontend/` |
| `tools/**`, `scripts/**`, `.claude/**` | `python -m unittest tools.test_agent_coordination tools.test_agent_scope tests.test_claude_hooks -v` | корень репозитория |
| `scripts/check_git_files.py` | `python scripts/check_git_files.py --staged` | корень репозитория |
| `docs/**`, `*.md` | проверка не требуется; проверить, что ссылки в тексте указывают на существующие файлы | — |

Формат frontend: `npm test` = `node --test` (встроенный раннер Node), установленные
пакеты не нужны. `npm run build` требует `node_modules`; в новом worktree — `npm ci`
в папке `frontend/` (правило из `docs/GIT_WORKFLOW.md`).

## 2. Прогнать

- Python: интерпретатор venv проекта, а не системный. Если venv нет и ставить
  пакеты нельзя — так и написать в отчёте, а не заменить проверку «на глаз».
- Каждая команда — отдельный запуск; ошибки смотреть в первом упавшем блоке.
- Упавший тест чинить до зелёного состояния или явно помечать как pre-existing.

## 3. Отчёт

Статус каждой проверки — ровно один из четырёх (контракт в `AGENTS.md`):

| Статус | Когда |
|---|---|
| `PASS` | проверка выполнена и зелёная |
| `FAIL` | выполнена и красная; приводится первый блок ошибки |
| `BLOCKED` | выполнить нельзя: причина и то, что её снимет |
| `NOT_RUN` | не выполнялась: причина |

Формат:

```
Проверка: <точная команда>
Статус: PASS | FAIL | BLOCKED | NOT_RUN
<первый блок ошибки, если есть>
```

Отчёт без `BLOCKED`/`NOT_RUN` обычно означает, что непроверенное выдано за
проверенное. «Тесты зелёные» без проверок по типу задачи — тоже не отчёт; набор
реальных проверок — в `.claude/rules/quality.md`.

Что нельзя делать при проверке:

- запускать платный API (`scripts/live_piapi_test.py`, `scripts/watch_hunyuan_test.py`);
- ставить системные пакеты;
- писать в `backend/studio.sqlite3` и другие реальные данные;
- объявлять проверку пройденной, если команда не запускалась.

## 4. Definition of Done

- код работает, а не только компилируется;
- на изменение есть тест, который до правки падал (red → green);
- результат проверен по типу задачи (`.claude/rules/quality.md`);
- ограничения обхода не пропущены молча: если проверка невозможна — `BLOCKED` с
  причиной;
- handoff обновлён, решение по приёмке принимает ревьюер.

## 5. Проверить, что проверка вообще работает

Новый тест доказывается красным до исправления и зелёным после:

```powershell
python -m unittest tests.test_claude_hooks -v
```

Если тест зелёный и до правки, он ничего не проверяет — переписать.
