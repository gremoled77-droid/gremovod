# Дизайн-петля для экранов студии

Адаптация метода «design loop»: сборщик строит кусок экрана, три критика с чистым контекстом судят **отрендеренный результат**, а не код. Критик, который помнит, как собиралась работа, проверяет собственную домашку.

Эталон здесь не «красиво», а конкретные макеты `docs/design/` и токены `frontend/src/design.css`. Проверяемые правила лежат в [bar.md](bar.md). Читать их перед работой.

## Правила студии, которые петля не отменяет

- Ключи API не печатать и не коммитить. Платные вызовы только через оценку цены и подтверждение владельца. Петле платная генерация не нужна.
- Новый экран получает класс на `<main>` (`home-main`, `create-main`, `storyboard-main`), иначе старая боковая панель и `margin:auto` ломают сетку.
- Проверки перед коммитом: из `frontend/` `npx tsc --noEmit`, `npm run build`, `npm test`; форматирование `npx prettier --write <файлы>` по `frontend/.prettierrc.json`.
- Общаться с владельцем по-русски, интерфейс тоже на русском.

## Фаза 1. Интервью

Задай ровно три вопроса сразу и жди ответа:

1. Какой экран и какого объёма (весь экран, один блок, телефонная версия)?
2. Эталон: какой макет из `docs/design/` (Main, Board, Mobile, Workflow) или уже готовый экран («Старт», «Кадры», «Раскадровка»), либо «пропускаю».
3. Какие файлы брать за основу (компонент в `frontend/src`, CSS, данные)?

Размытый ответ переспроси один раз. При «пропускаю» предложи три кандидата в эталоны и жди выбора. Без ответа бери самый жёсткий: ближайший готовый экран нового дизайна.

## Фаза 2. Проверка готовности

До любой работы отчитайся одним блоком:

- Эталон открыт (макет `docs/design/*.dc.html` в браузере или скриншот готового экрана).
- Результат можно отрендерить: фронтенд на :5173, бэкенд на :8000 (`/api/health`). Не запущено — скажи, не запускай молча. Скриншоты через встроенный браузер, десктоп 1440×900 и телефон 390×844.
- Входные файлы прочитаны.
- Итог: что работает, чего не хватает, какой критик ослепнет. Молча продолжать с критиком, который ничего не видит, нельзя.

## Фаза 3. Разбор эталона

Возьми готовый [bar.md](bar.md) и дополни его для этого экрана 5–7 механиками. Механики проверяются глазами и числами: «заголовок панели 15 px, подписи 12 px, служебные 10 px», «акцент #F2B134 не более двух раз на экран». Прилагательные не годятся. Покажи владельцу итоговый список и жди «ок» до сборки.

## Фаза 4. Петля

1. Раздели экран на 3–4 куска (например: шапка и навигация, основная область, правая панель, телефон).
2. На каждый кусок: сборщик правит код, затем **три критика отдельными субагентами** (Agent) со свежим контекстом. Критик получает только то, что ему положено, и не получает рассказа о том, как делалось.
3. Выход — победа (все критики прошли на всех кусках) или остановка владельцем. Числа кругов нет, но на каждом круге называй номер круга и пройденные куски.

### Три критика

| Критик | Что получает | Что судит | Чего не видит |
| --- | --- | --- | --- |
| ТЗ | текст задачи владельца + скриншот | сделано ли заявленное, все ли состояния и русские подписи на месте | красоту не оценивает |
| Системы | токены `design.css`, [bar.md](bar.md) + скриншот и вычисленные стили | палитра, шрифт, радиусы, размеры, класс на `<main>`, запрещённые приёмы | |
| Ремесла | скриншот результата и скриншот эталона **без подписей, вслепую** | ритм, плотность, иерархия, выглядит ли как из одной семьи с эталоном | код |

Правила критиков:

- Жёсткие. Похвала бесполезна. Вердикт двоичный (прошёл / не прошёл), при провале назвать самую большую дыру одной строкой.
- Судят по отрендеренному результату в браузере, не по коду. Исключение: критик системы видит вычисленные стили (`getComputedStyle`), чтобы проверить числа.
- Пройти должны все трое. Любой провал возвращает кусок на переделку.
- Критики ТЗ и системы могут быть на более простой модели. Критик ремесла — на самой сильной из доступных и никогда не понижается.

### Живая страница прогресса

Веди короткий файл `design-loop-progress.md` в scratchpad сессии (не в репозитории): куски, вердикты по трём критикам, история дыр, номер круга. Покажи владельцу после каждого круга.

## Цена

Честного самоотчёта по токенам не бывает. Показывай номер круга и пройденные куски, а потолок кругов, если владелец его назвал, считай контрольной точкой: дойдя до неё, остановись и спроси.

## Что ломает метод

- Размытая планка («как у Apple», «сделай красиво»): держи эталон конкретным.
- Сборщик судит сам себя: критики всегда отдельные субагенты.
- Мягкий критик: переспроси его жёстче, если вердикт «прошёл» без единого замечания.
- Фиксированное число кругов: выход только по победе или по слову владельца.
- Переуточнение: три вопроса один раз, дальше работа.

## Конец

Когда все куски прошли: `npx tsc --noEmit`, `npm run build`, `npm test`, prettier, скриншоты десктопа и телефона владельцу. Коммит и push только по просьбе владельца.
