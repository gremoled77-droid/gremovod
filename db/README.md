# GremoVOD — память студии / безопасная P0-миграция

## Исправления Codex: R-01–R-03

`install_schema` сначала проверяет существующие P0-колонки (типы, PK, NOT NULL и defaults), затем применяет DDL и `quick_check` в одной транзакции. Сбой откатывает эту транзакцию, включая уже созданные таблицы и добавленную колонку; рабочая база не заменяется файлом backup. Старый P0 layout поддерживается добавлением nullable `p0_runs.expected_media_manifest`. При неизвестном layout установка прерывается без изменений. Отдельные P0-таблицы версии или новая production DB не создаются.

Перед производством trusted backend должен вызвать `p0_control.freeze_manifest(db, run_id=..., expected_source_revision=..., slots=[...])`. Каждая позиция содержит ровно `slot_id`, `kind` и булево `required`; план берётся из утверждённого источника, а не из списка уже доставленных файлов. Полный план сохраняется в `p0_runs`, а позиции получают MISSING-строки. В пределах исходной версии план неизменяем; повтор идентичного freeze безопасен. `manifest_ready` сверяет доставку с этим планом и блокирует удалённый обязательный слот, изменение его required/kind, чужую ревизию или отсутствующий hash. Optional-позиции можно пропускать. После смены snapshot/source требуется новый freeze и проверенная доставка актуальной версии; прежние asset-записи не удаляются автоматически.

`authorize` и `begin_submit` транзакционно блокируют другое незавершённое действие того же `run_id/slot_id/kind`, включая AUTHORIZED, UNKNOWN и ожидание отмены. Новый job ID, envelope, модель или request hash не обходят блокировку. UNKNOWN сохраняет резерв; следующая попытка возможна только после подтверждённого терминального результата предыдущей операции. Отдельные `video_generation` и `lip_sync` остаются разными действиями.

Три acceptance-регрессии и проверки гонок/отката теперь находятся в `backend/test_p0_regressions.py`, `backend/test_p0_migrate.py` и штатном CI. Защищённая owner auth, единый бюджет Studio и provider reconciliation этим исправлением не реализованы.

Существующий `backend/main.py` уже использует `studio.sqlite3` и таблицу `jobs`. Файл `schema.sql` **НЕ** должен создавать новую параллельную базу. Пять новых таблиц получают prefix `p0_`, чтобы старые проекты и генерации остались на месте.

| Задача | Новая таблица |
|---|---|
| Память и этап задания | `p0_runs` |
| Кошелёк / лимиты | `p0_budget_envelopes` |
| Точные платные запросы | `p0_jobs` |
| Все обязательные шоты и дорожки | `p0_scene_manifest` |
| Три критика, версия видео и сценария | `p0_review_snapshots` |

До промышленной интеграции критические разрешения владельца и доверенные результаты провайдера передаются в тестовых функциях как **внутренние параметры**; их ни в коем случае нельзя читать непосредственно из HTTP body/n8n JSON. Настоящие Studio session/ACL/CSRF, currency bounds, WAL/transaction review и provider reconciler вынесены в `docs/CODEX_DECISIONS.md` (D-001..D-012).

## Локальный просмотр — ничего не меняет

Нужно установить рабочий путь к существующему файлу `studio.sqlite3` в соответствии с переменными в `backend/main.py`; не полагаться на путь из примера:

```powershell
python -m scripts.p0_migrate --db "C:\ПРОВЕРЕННЫЙ_ПУТЬ\studio.sqlite3"
```

Инструмент выдаст `DRY_RUN_NO_WRITES` и `quick_check`.

## Только после ревью Codex — явное добавление таблиц

```powershell
python -m scripts.p0_migrate --db "C:\ПРОВЕРЕННЫЙ_ПУТЬ\studio.sqlite3" --apply --backup "D:\GremoVOD_Backups\studio-before-P0.sqlite3"
```

Backup обязателен, создаётся SQLite backup API, включая согласованный WAL snapshot. Backup target не должен существовать. Никакой автоматический rollback по реальной базе не проводится. **В этой ветке команда --apply на рабочей базе не запускалась.**

Для теста на пустой SQLite использовать отдельный каталог и `backend/test_p0_control.py`, `tests/test_p0_state.js`. Бюджет измеряется в целых центах; reserved + spent не превышает grant. Если provider submit стал UNKNOWN, резерв не освобождается и запрос автоматически **не** отправляется второй раз.

## Правила аварии

- **Два Resume:** только первый захватывает шаг при актуальной версии, второй получает BLOCKED.
- **Обрыв после POST:** UNKNOWN + possible_charge, без автоматического повторного вызова.
- **Изменились prompt, модель, профиль или канон:** прежнее разрешение не работает.
- **Недостаёт обязательного кадра/звука:** монтаж нельзя допускать.
- **Ролик отсутствует:** A6/A7/A8 final media и READY BLOCKED.

n8n cloud не может запускать `ffprobe` на локальном компьютере. Mock FFmpeg-pilot проверяется отдельно в GitHub Actions, а доверенный локальный media worker с outbound-связью нужно интегрировать Codex.
