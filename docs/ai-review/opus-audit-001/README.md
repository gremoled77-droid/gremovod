# GremoVOD — пакет первого архитектурного аудита Claude Opus 5.5 (AUDIT-001)

**Статус пакета:** PREPARED / OFFLINE. Аудит ещё не проводился. Заключений Opus здесь нет.
**Дата подготовки:** 2026-10-20.
**Режим подготовки:** без единого платного API-вызова. Расходы на этапе подготовки — **0**.

---

## 1. Зачем этот пакет

GremoVOD — студия производства ИИ-контента (FastAPI + SQLite + React/Vite + n8n). Проект
развивается несколькими параллельными ветками, и три ключевые ветки сейчас висят
**незакрытыми Draft PR**. Из-за этого возникает главный риск: **код из разных Draft PR
выглядит как единая система, хотя в `main` его нет**.

Этот пакет — единственный вход для независимого архитектурного аудита. Цель аудита —
не «написать отчёт красиво», а ответить на узкий набор вопросов, которые владелец
не может закрыть сам, потому что для этого нужен независимый взгляд на P0-контур
(деньги, авторизация, SQLite, восстановление) и на честность заявлений о
независимых критиках.

Пакет собран так, чтобы аудитор **не искал** ничего: все нужные файлы, ревизии,
фрагменты кода и результаты прогнанных тестов уже внутри.

---

## 2. Что НЕ входит в пакет

- Никаких реальных медиа, баз данных, ключей и рабочих данных владельца.
- Никаких платных провайдеров (PiAPI, KIE, ElevenLabs, Fish Audio) — только спецификация
  и офлайн-тесты.
- Никаких выводов «это хорошо / это плохо» от автора пакета. Есть только **доказательства
  и вопросы**. Оценка — работа Opus.

## 4. Как читать пакет

| Файл | Назначение | Когда нужен |
|---|---|---|
| `PROJECT_CONTEXT.md` | Что такое GremoVOD, зачем, ключевые решения владельца | Перед всем |
| `ARCHITECTURE_MAP.md` | Карта модулей, зависимостей, зрелости реализации | AUDIT-001A, 001B |
| `P0_EVIDENCE.md` | Реальные контракты и фрагменты кода по деньгам/авторизации/SQLite | **AUDIT-001A** |
| `WORKFLOW_EVIDENCE.md` | n8n-схемы, контракты, маршруты, артефакты | **AUDIT-001B** |
| `QA_EVIDENCE.md` | Контракты A6/A7/A8, независимость, проверяемость | **AUDIT-001C** |
| `TEST_RESULTS.md` | Реально выполненные команды, exit codes, что не запускалось | AUDIT-001C |
| `OPEN_ISSUES.md` | Подтверждённые незакрытые вопросы | AUDIT-001C |
| `EVIDENCE_MANIFEST.json` | Пути, ревизии, объём, статус проверки каждого артефакта | Сверка |
| `OPUS_SYSTEM_PROMPT.md` | Правила строгого архитектурного аудита | Перед AUDIT-001A |
| `OPUS_FIRST_REQUEST.md` | Готовое первое сообщение | **AUDIT-001A** |
| `KIE_SETUP.md` | Подключение Opus 5.5 через KIE (2 варианта) | Перед любым запросом |

Три самостоятельных пакета запросов — в `packages/`:

- `packages/AUDIT-001A.md` — P0: деньги, авторизация, SQLite, состояния, восстановление
- `packages/AUDIT-001B.md` — n8n, контракты конвейера, маршруты медиа
- `packages/AUDIT-001C.md` — независимые критики, результаты проверок, межмодульная согласованность

Каждый пакет **самодостаточен**: Opus не обязан иметь доступ к GitHub, к предыдущим
API-вызовам и к памяти о прошлых этапах. Пакет B и C начинаются с повторного изложения
контекста, а не с «как мы выяснили в прошлый раз».

### Как отправить

| Путь | Что делать | Когда |
|---|---|---|
| **Скрипт** | `python packages\build_payloads.py` → `python packages\send_audit.py AUDIT-001A` | Рекомендуемый: собирает запрос, вложения и сохраняет ответ |
| **Вложения вручную** | Прикрепить 5 `.txt` из `packages/attachments/AUDIT-001A/` + system prompt + текст запроса | Если ваш инструмент принимает файлы |
| **Всё одним текстом** | Скопировать `packages/payloads/AUDIT-001A.payload.txt` целиком в поле сообщения | Если прикрепить нельзя вообще |

> ⚠️ **KIE отвергает `.md` и `.json`** — не из-за содержимого, а из-за `media_type`
> (`text/markdown` и `application/json` не поддерживаются). Поэтому все вложения
> имеют расширение `.txt` (`text/plain`) — байты те же. Подробно: `KIE_SETUP.md` §8.

## 5. Порядок запуска

1. Прочитать `PROJECT_CONTEXT.md` и `ARCHITECTURE_MAP.md`.
2. Настроить доступ к KIE по `KIE_SETUP.md` (два независимых варианта — **не смешивать**).
3. Выполнить **минимальный тест подключения** из `KIE_SETUP.md` §6 — отдельно от аудита.
4. Отправить `packages/AUDIT-001A.md` как первое сообщение.
5. Дождаться ответа. **Не отправлять B и C автоматически** — каждый следующий пакет
   готовится после разбора предыдущего.
6. Зафиксировать ответ Opus в отдельный файл `responses/` (пакет не содержит чужих
   заключений, чтобы их нельзя было спутать с выводами автора).

## 6. Правила для аудитора (дублируются в `OPUS_SYSTEM_PROMPT.md`)

- Ссылаться на **файл:строку** и **SHA**, а не на пересказ.
- Если чего-то нет в пакете — так и написать («не найдено»), а не достраивать.
- Не считать зелёные тесты доказательством отсутствия архитектурных дефектов.
- Разделять `IMPLEMENTED / PARTIAL / SPEC-ONLY / MOCK` — в проекте эти состояния
  принципиально различаются, и «зелёный workflow» в MOCK-режиме ничего не доказывает.
- Не предлагать «просто добавить проверку» там, где отсутствует само доказательство
  (например, реальный MP4 для A8).
