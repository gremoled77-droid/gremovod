## 1. Денежный контур

### OI-01 — P0-контур защищает только свой путь; в `main` платные вызовы идут мимо него

**Тип:** дефект/риск · **Приоритет:** высший
> **Уточнение GPT-6 Astra:** доказан обход P0 **на `main`**. Это не доказывает
> обход всего legacy-учёта и не описывает состояние после будущего merge —
> это надо проверять пробным merge.

На `main` все платные вызовы идут через `adapters` и `main.py`:

```python
# backend/main.py:460-472
key = provider_key('kie') if spec['provider']=='kie' else get_key(x_api_key)
...
if spec['provider']=='kie': result = await kie.submit(key, adapters.wire_body(spec,payload))
else: result = await request_piapi('POST', adapters.submit_path(spec), key, adapters.wire_body(spec,payload))
```

Весь P0-контур PR #29 (`p0_authz`, `p0_control`, `spend_ledger.check_cents`,
`p0_provider_dispatch`) в `main` **отсутствует**. То есть capability, единый бюджет,
`submit_count` и запрет второй БД **не защищают** ни один реальный платный вызов в
`main`. PR #29 добавляет второй, защищённый путь — но не заменяет первый.

**Подтверждение:** `git ls-tree -r --name-only origin/main -- backend` не содержит
`p0_authz.py`, `p0_control.py`, `p0_provider_dispatch.py`; `backend/security.py` в
`main` не содержит `p0_`.

**Вопрос аудитору:** каким механизмом гарантируется, что после мержа P0-контур
не будет обойдён? Есть ли в `p0_provider_dispatch.py` принудительное перенаправление
`main`-пути, или это две независимые реализации одного и того же?

### OI-02 — Для состояния `UNKNOWN` нет процедуры сверки

**Тип:** дефект · **Приоритет:** высокий

`p0_control.mark_unknown` (`backend/p0_control.py:308-316`) оставляет задачу в
`UNKNOWN` с `possible_charge=1`, деньги остаются зарезервированными, повтор
запрещён. Это правильно. Но **механизма приведения такой задачи к терминальному
состоянию нет** — ни в `p0_control.py`, ни в `p0_provider_dispatch.py`.

**Подтверждение:** `VALIDATION.json` → `codex_p0_fixes_2026_10_19.remaining`:
```json
"remaining": ["R-04 shared budget", "R-05 trusted runtime auth",
              "UNKNOWN provider reconciler", "real asset transport and QA"]
```
Пункт «UNKNOWN provider reconciler» значился как незакрытый **до** PR #29; PR #29
закрыл R-04 и R-05, но **reconciler не появился** (в `p0_control.py` нет функции,
переводящей `UNKNOWN` в терминальное состояние, кроме `finish_verified`, который
требует `state == "SUBMITTED"` — то есть из `UNKNOWN` недостижим).

**Следствие:** деньги за «зависшие» задачи зарезервированы, пока не придёт
терминальное событие; лимит проекта постепенно выедается. Это fail-closed по
безопасности, но **по стоимости** — накопление.
> **Уточнение GPT-6 Astra:** формулировка «дневной лимит навсегда» требует
> изучения календарного учёта — как именно `spend_ledger.py:89-110` считает
> переход через полночь. Это не проверено.

### OI-03 — Нет провайдерского idempotency-key

**Тип:** вопрос · **Приоритет:** высокий

Весь контур опирается на то, что второй POST не произойдёт (`submit_count`,
`UNKNOWN`-блокировка, `state_version`). Но **если первый POST ушёл, а ответ
потерялся**, повторно отправить тот же запрос безопасно нельзя — а провайдерский
idempotency-key, который сделал бы повтор безопасным, в контуре не используется.

**Подтверждение:** в `backend/p0_control.py`, `backend/p0_provider_dispatch.py`,
`backend/adapters.py` (main) нет ни `idempotency`, ни `Idempotency-Key`.
> **Уточнение GPT-6 Astra:** отсутствие заголовка `Idempotency-Key` не доказывает
> отсутствие эквивалентного механизма на стороне API провайдера. Поддержка
> провайдером — неизвестна.

**Вопрос аудитору:** как предлагается безопасно закрывать разрыв «запрос ушёл,
ответ потерян»? Текущая политика — заблокировать слот навсегда.

### OI-04 — Окно между `submit_count=1` и фактическим HTTP POST

**Тип:** вопрос · **Приоритет:** средний

`p0_control.begin_submit` (`backend/p0_control.py:288-306`) коммитит
`state='SUBMITTING', submit_count=1` **до** того, как вызывающий код делает POST.
Документстринг это фиксирует: «caller makes at most one POST».

Но если процесс умирает между коммитом и POST — задача навсегда в `SUBMITTING`,
деньги зарезервированы, провайдер их не списал. Восстановления нет (см. OI-02).

**Вопрос аудитору:** допустимо ли такое окно, и какая процедура его закрывает?

### OI-06 — «Трёхкритический» гейт фактически двухкритический

**Тип:** дефект (расхождение спека↔код) · **Приоритет:** высокий

### OI-11! — `VALIDATION.json: "status": "PASS"` при `scope: "documentation structure only"`

**Тип:** расхождение (риск прочтения) · **Приоритет:** средний

```json
{
  "status": "PASS",
  ...
  "scope": "documentation structure only",
  "not_tested": ["n8n execution", "provider calls", "media generation",
                 "actual billing", "behavioral critic quality"]
}
```

`PASS` относится к структуре документации. `not_tested` прямо перечисляет
исполнение n8n, вызовы провайдеров, генерацию медиа, реальное списание денег и
**поведенческое качество критиков**. Читатель, не дочитавший до `scope`,
примет `PASS` за «конвейер проверен».

**Это не обвинение автора** — `scope` и `not_tested` написаны явно и честно.
Это находка о **читаемости**: в проекте, где «PASS» и «не проверено» лежат в
одном файле в 10 строках друг от друга.
> **Уточнение GPT-6 Astra:** scoped `PASS` вместе с `not_tested` логически
> **корректен**. Это риск отображения статуса без scope, а не противоречие.

## 4. Гигиена и окружение

### OI-12 — Путь БД по умолчанию — внутри репозитория

**Тип:** риск · **Приоритет:** средний

```python
# backend/main.py:22-24
DATA = Path(os.environ['STUDIO_DATA_DIR']).resolve() if os.environ.get('STUDIO_DATA_DIR') else None
DB = (DATA or ROOT)/'studio.sqlite3'
```

Без `STUDIO_DATA_DIR` БД создаётся как `backend/studio.sqlite3` — внутри рабочей
копии Git. Путь в `.gitignore` есть, но:
- тесты, запущенные без переменной, **создают и меняют БД в репозитории**;
- БД физически зависит от расположения кода.

При подготовке пакета это потребовало явного `STUDIO_DATA_DIR` во всех прогонах
(см. `TEST_RESULTS.md` §1). PR #29 добавил `studio_db.resolve()` с отказом на второй
БД — но путь **по умолчанию** не изменил.

### OI-15 — `CLAUDE.md` описывает архитектуру, которая не совпадает с кодом

**Тип:** расхождение · **Приоритет:** средний

`CLAUDE.md` перечисляет модули и компоненты (`App.tsx`, `StageNav`, `Dock`,
`HomeScreen`, `CreateScreen`, `ProductionStoryboard`, `WorkflowPanel/workflowPlan`,
`GenerationReview`, `ActivityContext/useActivity`, `GenerationWatcher`).

всей работы вне `main`. Аудитору это объясняет заранее (см. `PROJECT_CONTEXT.md` §C).
> **Уточнение GPT-6 Astra:** описание `main`, актуальное для `main`, **не становится
> неправильным** из-за отсутствия Draft-функций других веток. Риск — в подсистеме
> вывода, а не в самом тексте.
