## A. Назначение

**GremoVOD** — однопользовательская (private, self-hosted) студия производства
ИИ-контента. Пользователь описывает идею, студия превращает её в сценарий, раскадровку,
набор изображений, видео, нативный звук, TTS, SFX и музыку, монтирует и выпускает.

Продуктовая идея: **видео-канал, где сценарий, визуальный канон, звук и монтаж
согласованы между собой**, а не собраны из независимых генераций. Отсюда вся
архитектура: канон (canon) — источник правды для всех последующих стадий; каждый
артефакт должен быть привязан к ревизии канона.

Пользователь — владелец студии (один человек), поэтому «пользователь» в коде почти
всегда означает владельца, а не многопользовательскую роль.

## B. Технологический стек (проверено в коде)

- **Backend:** Python 3.13, FastAPI, stdlib `sqlite3`. Зависимости зафиксированы в
  `backend/requirements.lock.txt` (снимок проверенного Windows-окружения).
  `backend/requirements.txt` — верхние границы диапазонов.
- **Frontend:** React 18 + TypeScript + Vite. `frontend/package.json`:
  `@xyflow/react` (графы воркфлоу), `lucide-react`, `typescript`.
- **Оркестрация:** n8n. JSON-описания воркфлоу в `workflows/`, скрипты импорта в

- **Провайдеры:** PiAPI (основной шлюз), KIE, ElevenLabs, Fish Audio — см. `backend/kie.py`,
  `backend/adapters.py`, `backend/sound.py`.
- **Хранилище:** один SQLite (`studio.sqlite3`) + файловые каталоги под медиа.

## D. Ключевые решения владельца (из `docs/CODEX_DECISIONS.md`, PR #29)

- **D-010.** Формирование QA-вердикта: N34 = только техконтроль, без LLM; N35 = замороженное
  evidence; три независимых A6/A7/A8 — только с реальным покрытием.
- **Платные провайдеры.** Не тратить реальные кредиты без подтверждённого API,
  доступного лимита, модели/цены и **явной авторизации конкретного запроса**, которую

## E. Честное состояние на дату пакета

Это не жалоба и не оценка — это факты, которые аудитор обязан знать, чтобы не
принять MOCK за production.

1. **`main` не содержит P0-контура.** Ни бюджета, ни capability-авторизации, ни
   запрета второй БД. Это в PR #29.
2. **WF_00–WF_06 в репозитории — MOCK.** Их `name` содержит `MOCK ONLY (SOURCE EXPORT)`,
   `active=false`, WF_01–WF_06 содержат по 2 узла. Манифест сам объявляет
   `status: "MOCK_FIRST_NOT_PUBLISHED"`, `real_provider_enabled: false`,
   `real_media_evidence_available: false`. Подробно — `WORKFLOW_EVIDENCE.md`.
3. **A8 отключён.** Ремесленная оценка (native audiovisual) требует реального
   пользовательского MP4 и разрешения владельца, которых нет. `STATUS.md`:
   `MEDIA-01 → BLOCKED_NO_USER_MP4`.
4. **Реальные платные вызовы в конвейере не выполнялись.** По матрице N34–N41
   A8 — `DISABLED и BLOCKED, не SKIPPED`.

Что при этом **реализовано и покрыто тестами** — P0-контур PR #29 (свой бюджет,
HMAC-подписанные capability, запрет второй БД, UNKNOWN-состояние, дедупликация) и
бэкенд на `main` (242 теста, 345 в PR #29). Это важный баланс: проект не пустой и не
«нарисованный», но и не доведён до production.

```python
              'model': ROLE_MODELS[role], 'mock_only': True, 'quality_claim': False,
              'source_provenance': snapshot['source_provenance']}
    if role == 'REVIEW-REQ':
        return {**common, 'role': role, 'approved_requirements': snapshot['requirements'],
                'brief_revision': snapshot['brief_revision']}
    return {**common, 'role': role, 'approved_canon': snapshot['canon'],
            'canon_revision': snapshot['canon_revision']}
```

Четыре свойства, видимые прямо в коде:
1. `mock_only: True` — пакет **сам декларирует**, что модель моковая.
2. `quality_claim: False` — пакет не претендует на подтверждение качества.
3. `requested_scopes: ['TEXT']` — **только текст**.
4. A6 получает `approved_requirements`, A7 получает `approved_canon` — **роли разведены
   на уровне данных**, чужой материал в пакет не попадает.

### 2.2 Что входит в снимок

`context()` собирает: `artifact_text` (текст текущих сцен), `requirements`
(карточки story-plan + исходная идея), `canon` (текст `projects.state.characters[].identity`),
и четыре хэша: `artifact_revision`, `brief_revision`, `canon_revision`, `text_sha256`.

Проверено: в снимке жёстко зашито
```python
'canon_images_reviewed': False
```
и стоит защита от раздувания:
```python
if any(len(snapshot[k]) > 150000 for k in ('artifact_text', 'requirements', 'canon')):
    raise HTTPException(422, 'QA text snapshot is too large')
```

## D-03. Может ли критик технически проверить свой критерий

| Роль | Критерий | Что реально в пакете | Вердикт |

### 3.1 Особая оговорка про A7

Политика проекта (`QA_EVIDENCE_POLICY.md:3`) фиксирует ровно тот отказ, который
A7 воспроизводит в текущей реализации: «A7 сравнил тексты; никакого реального
автомобиля, кадра или видео не существовало». То есть A7, как он реализован,
делает **именно то, чего политика запрещает** — но формально это «PASS(TEXT)»,
который политика отдельно запрещает превращать в `IMAGE`/`VIDEO` PASS.

> **Вопрос аудитору:** является ли «A7 сравнил текст и выдал PASS» приемлемым
> результатом, если его собственная спецификация (`SKILL.md:19`) требует
> утверждённого серверного канона, а вход — свободный текст?

### 3.2 Следствие для «трёхкритического» гейта

Поскольку A8 не даёт **никакой** проверочной способности, а бэкенд агрегирует
**два** вердикта, фактически «трёхкритический независимый гейт» — это
**двухкритический текстовый гейт**. Он fail-closed и не пропускает ложное качество —
но это не тот гейт, который описан.

## 1. Денежный контур

### OI-01 — P0-контур защищает только свой путь; в `main` платные вызовы идут мимо него

**Тип:** дефект/риск · **Приоритет:** высший

На `main` все платные вызовы идут через `adapters` и `main.py`:

```python
# backend/main.py:460-472
key = provider_key('kie') if spec['provider']=='kie' else get_key(x_api_key)
...
if spec['provider']=='kie': result = await kie.submit(key, adapters.wire_body(spec,payload))
else: result = await request_piapi('POST', adapters.submit_path(spec), key, adapters.wire_body(spec,payload))
```

Весь P0-контур PR #29 (`p0_authz`, `p0_control`, `spend_ledger.check_cents`,
`p0_provider_dispatch`) в `main` **отсутствует**. То есть capability, единый бюджет,
`submit_count` и запрет второй БД **не защищают** ни один реальный платный вызов в
`main`. PR #29 добавляет второй, защищённый путь — но не заменяет первый.

**Подтверждение:** `git ls-tree -r --name-only origin/main -- backend` не содержит
`p0_authz.py`, `p0_control.py`, `p0_provider_dispatch.py`; `backend/security.py` в
`main` не содержит `p0_`.

**Вопрос аудитору:** каким механизмом гарантируется, что после мержа P0-контур
не будет обойдён? Есть ли в `p0_provider_dispatch.py` принудительное перенаправление
`main`-пути, или это две независимые реализации одного и того же?

### OI-02 — Для состояния `UNKNOWN` нет процедуры сверки

**Тип:** дефект · **Приоритет:** высокий

`p0_control.mark_unknown` (`backend/p0_control.py:308-316`) оставляет задачу в
`UNKNOWN` с `possible_charge=1`, деньги остаются зарезервированными, повтор
запрещён. Это правильно. Но **механизма приведения такой задачи к терминальному
состоянию нет** — ни в `p0_control.py`, ни в `p0_provider_dispatch.py`.

**Подтверждение:** `VALIDATION.json` → `codex_p0_fixes_2026_10_19.remaining`:
```json
"remaining": ["R-04 shared budget", "R-05 trusted runtime auth",
              "UNKNOWN provider reconciler", "real asset transport and QA"]
```
Пункт «UNKNOWN provider reconciler» значился как незакрытый **до** PR #29; PR #29
закрыл R-04 и R-05, но **reconciler не появился** (в `p0_control.py` нет функции,
переводящей `UNKNOWN` в терминальное состояние, кроме `finish_verified`, который
требует `state == "SUBMITTED"` — то есть из `UNKNOWN` недостижим).

**Следствие:** деньги за «зависшие» задачи зарезервированы навсегда; лимит проекта
постепенно выедается. Это fail-closed по безопасности, но **по стоимости** —
накопление.

### OI-03 — Нет провайдерского idempotency-key

**Тип:** вопрос · **Приоритет:** высокий

Весь контур опирается на то, что второй POST не произойдёт (`submit_count`,
`UNKNOWN`-блокировка, `state_version`). Но **если первый POST ушёл, а ответ
потерялся**, повторно отправить тот же запрос безопасно нельзя — а провайдерский
idempotency-key, который сделал бы повтор безопасным, в контуре не используется.

**Подтверждение:** в `backend/p0_control.py`, `backend/p0_provider_dispatch.py`,
`backend/adapters.py` (main) нет ни `idempotency`, ни `Idempotency-Key`.

**Вопрос аудитору:** как предлагается безопасно закрывать разрыв «запрос ушёл,
ответ потерян»? Текущая политика — заблокировать слот навсегда.

### OI-04 — Окно между `submit_count=1` и фактическим HTTP POST

**Тип:** вопрос · **Приоритет:** средний

`p0_control.begin_submit` (`backend/p0_control.py:288-306`) коммитит
`state='SUBMITTING', submit_count=1` **до** того, как вызывающий код делает POST.
Документстринг это фиксирует: «caller makes at most one POST».

Но если процесс умирает между коммитом и POST — задача навсегда в `SUBMITTING`,
деньги зарезервированы, провайдер их не списал. Восстановления нет (см. OI-02).

**Вопрос аудитору:** допустимо ли такое окно, и какая процедура его закрывает?

### OI-11! — `VALIDATION.json: "status": "PASS"` при `scope: "documentation structure only"`

**Тип:** расхождение (риск прочтения) · **Приоритет:** средний

```json
{
  "status": "PASS",
  ...
  "scope": "documentation structure only",
  "not_tested": ["n8n execution", "provider calls", "media generation",
                 "actual billing", "behavioral critic quality"]
}
```

`PASS` относится к структуре документации. `not_tested` прямо перечисляет
исполнение n8n, вызовы провайдеров, генерацию медиа, реальное списание денег и
**поведенческое качество критиков**. Читатель, не дочитавший до `scope`,
примет `PASS` за «конвейер проверен».

**Это не обвинение автора** — `scope` и `not_tested` написаны явно и честно.
Это находка о **читаемости**: в проекте, где «PASS» и «не проверено» лежат в
одном файле в 10 строках друг от друга.

### OI-12 — Путь БД по умолчанию — внутри репозитория

**Тип:** риск · **Приоритет:** средний

```python
# backend/main.py:22-24
DATA = Path(os.environ['STUDIO_DATA_DIR']).resolve() if os.environ.get('STUDIO_DATA_DIR') else None
DB = (DATA or ROOT)/'studio.sqlite3'
```

Без `STUDIO_DATA_DIR` БД создаётся как `backend/studio.sqlite3` — внутри рабочей
копии Git. Путь в `.gitignore` есть, но:
- тесты, запущенные без переменной, **создают и меняют БД в репозитории**;
- БД физически зависит от расположения кода.

При подготовке пакета это потребовало явного `STUDIO_DATA_DIR` во всех прогонах
(см. `TEST_RESULTS.md` §1). PR #29 добавил `studio_db.resolve()` с отказом на второй
БД — но путь **по умолчанию** не изменил.

D-1. СУЩЕСТВОВАНИЕ ТРЁХ КРИТИКОВ. A6 — соответствие заданию; A7 — согласованность
    мира, образов и непрерывности; A8 — ремесло. Определения существуют в двух

    N36/N37/N38 помечены `Реализация: ROLE_ONLY`. Оцени:
      - что именно реализовано, а что нет, по каждому из трёх;
      - достаточно ли того, что в `agent-manifest.json` у A6 — claude-haiku-5-5,
        у A7 — claude-sonnet-5-5, у A8 — claude-opus-5-5, и все три имеют
        `published: false`, чтобы считать роли подготовленными;
      - отдельно: A8 уже настроен на Claude Opus 5.5, а в спецификации сказано
        «A8 остаётся на Sonnet» — оцени это противоречие и то, какая сторона
        выглядит более свежей по датам и по связности с остальным материалом.

D-2. НЕЗАВИСИСИМОСТЬ. Требование: критик получает только артефакт, свою часть
    требований/канона/bar и минимальные ID; не получает историю изготовления,
    самооценку автора и вердикт другого критика. В коде `role_package()` выдаёт
    A6 `approved_requirements`, A7 — `approved_canon`, то есть роли разведены на
    уровне данных; `verify_verdict` отвергает цитаты из чужой роли. Оцени:
      - достаточна ли разделение по данным для заявленной независимости;
      - какие ещё каналы загрязнения независимости остаются (общий снапшот, общий
        `review_round`, общий токен/сессия, общий кэш, накопление истории);
      - достаточно ли `review_round_id` + `snapshot_hash` + `master_checksum`,
        чтобы доказать, что все критики смотрели один и тот же файл.

D-3. ТЕХНИЧЕСКАЯ ПРОВЕРЯЕМОСТЬ. Это главный вопрос. A6 получает текст и
    требования; A7 получает текст и `approved_canon`, который является свободным
    текстом из состояния проекта, при этом `canon_images_reviewed` жёстко `False`,
    а `requested_scopes`/`checked_scopes` ограничены `['TEXT']`; A8 не имеет роли
    в `ROLES` вовсе. Оцени:
      - для каждого из трёх — может ли он по фактическому входу вынести PASS/FAIL
        по своим критериям, а BLOCKED — по чужим;
      - является ли «A7 сравнил тексты и выдал PASS» допустимым результатом, если
        его собственная спецификация требует серверного утверждённого канона с
        `canon_revision`, а на входе — редактируемый пользователем текст без флага
        `approved`;
      - достаточно ли `Literal['TEXT']` как техническая гарантия, что текстовый
        вердикт никогда не будет выдан за медиа-вердикт, или нужна дополнительная
        защита;
      - что минимально необходимо, чтобы A7 стал способен проверить свой критерий,
        и что минимально необходимо для A8.

D-4. ФАКТИЧЕСКАЯ ПРОВЕРОСПОСОБНОСТЬ СЕГОДНЯ. Единственный исполняемый путь,
    порождающий вердикты A6/A7/A8, — `tools/mock_evidence.py:60`, и он жёстко
    отдаёт BLOCKED всем трём; тест `backend/test_mock_evidence.py` успешно это
    проверяет. В `WF_05_Assembly_And_Critics.json:30` — тоже жёсткий BLOCKED.
    Оцени:
      - означает ли зелёный тест, что система ничего не проверяет, — или что она
        проверяет ровно то, что задумано (fail-closed), и это корректно;
      - как должен выглядеть чек-лист, чтобы в репозитории нельзя было случайно
        принять MOCK-вердикты за реальную приёмку;
      - что должно произойти в системе, если роль вердикта окажется неполной
        (например, пришли только A6 и A7) — сейчас это видно только в коде
        агрегации, а в спецификации — нет.

D-5. ГЕЙТ БЕЗОПАСНОГО СОЕДИНЕНИЯ. Документ
    `integrations/n8n/QA_A6_A7_SECURE_CONNECTION_GATE_2026-10-19.md` (только в PR #8;
    в pr/29 его нет) описывает требуемый контракт перед живыми моделями:
    изолированная сессия на критика, серверное хранение разрешения стоимости,
    игнорирование клиентского `approved=true`, машинная проверка схемы и точных
    цитат, 409 на устаревших входах. Реально в коде обеспечено: loopback+токен,
    разделение владелец/сервис, отвержение устаревших ревизий, побайтовая
    сверка цитат, запрет чужих цитат, лимит тела 32 КБ, идемпотентность,
    fail-closed агрегация. Не обеспечено: транспорт n8n→FastAPI, живой вызов
    Agent, серверное разрешение стоимости, инспекция медиа. Документ сам пишет,
    что `messageAnAgent` deprecated/retired, что «доступ к QA через сам workflow
    по-прежнему отсутствует», а единственная попытка живого вызова A6 провалилась
    3× с `AI_APICallError`, и что возможные списания по ошибочным попыткам
    неизвестны. Оцени:
      - что именно этот гейт доказывает, а что — нет, и насколько его название
        («secure connection») соответствует содержанию, если реализована только
        серверная половина;
      - достаточно ли изоляции по loopback+токену, учитывая, что агент при этом
        должен обращаться к сервису из облака n8n — то есть требование «только
        loopback» само по себе делает живое подключение невозможным, и как
        разрешить это противоречие без ослабления контроля;
      - стоит ли вопрос «возможны ли списания по ошибочным попыткам» считать
        риском бюджета, и что для этого нужно.

D-6. ЧЕСТНОСТЬ ЗАЯВЛЕНИЙ. По всему проекту A6/A7/A8 упоминаются в 18+ файлах
    pr/29, причём в основном только в прозе (docs/CODEX_DECISIONS.md,
    ASTRA_FIXES_V1_1.md, N34_N41_RUNTIME_MODEL_MATRIX.md, NODES.md, nodes.json и
    др.), а в исполняемом коде — только как жёстко зашитые BLOCKED. При этом
    `VALIDATION.json` объявляет `status: "PASS"` при `scope: "documentation
    structure only"`. Оцени:
      - где в проекте граница между «заявлено» и «сделано» проведена достаточно
        явно, а где её нет;
      - является ли `PASS` в `VALIDATION.json` рядом с `not_tested` проблемой
        формулировки, и какой вариант формулировки был бы лучше;
      - что конкретно стоит поправить в первую очередь, чтобы сторонний читатель
        репозитория не принял спецификацию за работающую систему.

D-7. ОРТОГОНАЛЬНОСТЬ КОНТРАКТОВ. В проекте три независимых контракта вердикта:
    (1) `integrations/n8n/contracts/qa-reviewer-output-v1.schema.json` — роли
    REVIEW-REQ/REVIEW-SYSTEM/REVIEW-CRAFT, scope TEXT/IMAGE/VIDEO/AUDIO, evidence
    с типами; код его **не загружает** (в TODO.md:439 — нереализованный пункт);
    (2) Pydantic-контракт в `backend/qa_text_precheck.py` — строже и уже: две роли,
    только TEXT, только mock-модели, `Literal[0]` по стоимости;
    (3) `dev-run-summary/1` в PR #35 — для ревью git-диффов, ролей и scope не
    имеет вовсе. Оцени:
      - насколько три контракта должны быть разными по назначению и не является ли
        их пересечение по именам (`PASS`) источником путаницы;
      - что будет, если контракт (1) начнут применять по плану — какие расхождения
        вылезут первыми;
      - стоит ли `dev-run-summary/1` (MOCK-ревьюер кода) вообще упоминаться рядом
        с A6/A7/A8 в одном документе, или это смешивает два разных контура.

D-8. СКВОЗНАЯ СОГЛАСОВАННОСТЬ. Соедини три наблюдения, которые по отдельности
    выглядят безобидно:
      (а) в `main` платные вызовы идут через `adapters` и `main.py:460-472` мимо
          P0-контура, который есть только в PR #29;
      (б) `freeze_manifest` (FastAPI) и узлы S01/S08 (спецификация n8n) — две
          независимые модели версионирования, причём S01/S08 не исполняются;
      (в) `spent_limit.test.mjs` и `test_p0_state.js` проверяют бюджет, а
          `wf_03`/`wf_04` в спецификации предполагают платные вызовы TTS/SFX и
          видео, но в MOCK-режиме.
    Оцени: где именно проходит граница «зелёные тесты перестают защищать»,
    и какие три проверки, добавленные в репозиторий, дали бы наибольший эффект
    на реальный риск. Это вопрос о том, **что тестировать дальше**, а не о том,
    какие ещё тесты написать ради числа.
