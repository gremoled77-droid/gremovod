### Почему тронут `.gitignore`

Правило `tools/` в `.gitignore` молча игнорировало новые файлы внутри `tools/ai_review/`:
`tools/ai_review/argon_review.py` из PR #22 попал в репозиторий только через принудительный `git add -f`.
Добавлена точечная инверсия (`!tools/` → `tools/downloads/` → `tools/ffmpeg/` → `!tools/ai_review/`), поэтому
новые файлы шлюза видны `git status`, а локальные бинарники (`tools/downloads/`, `tools/ffmpeg/`) и `__pycache__`
остались проигнорированными. Проверено: `git check-ignore` даёт «не игнорируется» для трёх новых файлов
и «игнорируется» для `__pycache__`, `tools/downloads/` и `tools/ffmpeg/`.

## 3а. Независимое ревью и найденные дефекты

Код шлюза был отдан на независимую проверку (отдельный агент-ревьюер, только чтение, без правки
файлов, 7 зондов в `%TEMP%`). Ревьюер подтвердил пробами, что гонка за ledger между 8 процессами
даёт ровно одну резервацию, гонка за слот — ровно один слот, пути ретрая нет, `usd_amount` всегда
`null`, битый ledger не обнуляет лимиты, а резервирование действительно происходит до HTTP.

Найдено 8 дефектов — **все исправлены** отдельным коммитом, на каждый добавлен тест:

| # | Серьёзность | Дефект | Исправление |
|---|---|---|---|
| 1 | высокая | Одобрение без `head_sha` проходило для **любого** head — платное ревью могло идти по коду, который владелец не одобрял | `head_sha` теперь обязателен и должен совпадать; иначе `PENDING_APPROVAL / approval_stale` |
| 2 | средняя | URL PR использовался как есть: `…/pull/1` и `…/pull/1/` давали разные ключи ledger и **два** платного вызова | `canonical_pr()` — один ключ на PR независимо от завершающего слэша |
| 3 | средняя | Дневной кредитный потолок суммировал только `credits_consumed` от провайдера; если провайдер его не присылает, потолок становился пустым | Учитывается наблюдаемая дельта баланса; в ledger пишется фактический расход; превышение потолка за один вызов → `MISMATCH` |
| 4 | средняя | `findings` не-массив ронял `run()` с необработанным исключением, отчёт не писался | Проверка типов → `HALTED_UNKNOWN / response_not_json` |
| 5 | средняя | Противоречивый ответ `{"verdict":"PASS","findings":[…]}` засчитывался как PASS | → `HALTED_UNKNOWN / contradictory_verdict`, findings остаются в отчёте |
| 6 | средняя | Сырой ответ провайдера попадал в коммитируемый отчёт; длинный токен вида `SUPERSECRETKEY1234567890` не маскировался | Сырой ответ убран из отчёта (лежит в `<state-dir>\answers\`); в отчёте только разобранные findings; добавлено маскирование длинных непрозрачных токенов, git SHA остаются читаемыми |
| 7 | низкая | Ошибка ledger при резервировании оставляла занятый слот одновременности на 15 минут | Слот освобождается при любом исходе резервирования |
| 8 | низкая | `network_calls` оставался 0 после неудачного запроса — отчёт занижал расход; неверная политика окружения вылетала из `run()` | Счётчик вызовов ставится перед отправкой; `Policy.from_env()` внутри защитного блока |

Отдельно в ходе проверки опубликованных команд найдены и исправлены два дефекта самого `argon_review.py`:

- **Бинарный маркер искался подстрокой по всему diff.** Любой diff, который *упоминает* слова
  `Binary files `, отвергался как бинарный — включая diff самого `argon_review.py`, чей исходник
  содержит эти слова. Теперь маркер распознаётся только в начале строки (`has_binary_patch()`).
- **Сторож секретов ловил собственные тестовые фикстуры.** Фикстуры с ключами теперь собираются
  в рантайме (`"sk-" + "abcdefghijklmno123456"`), а в генераторе примеров ключ начинается со
  `example-` — значение из белого списка регулярки. Смысл тестов не изменился, но diff репозитория
  больше не выглядит как утечка.

## 3б. Находки при проверке моста на собственном репозитории

Шлюз прогоняли на самом GremoVOD — `build_review_packet.py` и `review_gate.py --mode offline`
против `origin/main..HEAD` этого PR. Прогон вскрыл четыре расхождения с контрактом владельца,
все исправлены в `1209dfe`.

| # | Серьёзность | Расхождение | Исправление |
|---|---|---|---|
| 1 | высокая | **Лимиты менялись окружением без пола.** `Policy.from_env()` читал `ARGON_MAX_CALLS_PER_DAY` и прочие как есть, поэтому агент, который обязан укладываться в бюджет, мог экспортировать `ARGON_MAX_CALLS_PER_DAY=500` и тратить сколько угодно. Требование «агент не меняет лимиты» формально не выполнялось | Потолки в коде: `HARD_MAX_CALLS_PER_PR=1`, `HARD_MAX_CALLS_PER_DAY=2`, `HARD_MAX_CALLS_PER_WEEK=5`, `HARD_MAX_PACKET_BYTES=6144`, `HARD_MAX_PACKET_FILES=4`, `HARD_MAX_CONCURRENT=1`, `RETRY_COUNT=0`. Окружение может только **сузить** лимит; факт приведения к потолку пишется в отчёт. Потолок применяется и в точке вызова, поэтому `Policy`, собранный в Python, тоже не даёт большего бюджета |
| 2 | высокая | **Второй путь трат.** `argon_review.py --live` тратил кредиты сам: интерактивное подтверждение — и всё. Без ledger, без потолков на PR/сутки/неделю, без кредитных лимитов и без файла одобрения. Любой второй путь трат — это обход всех ограничений сразу | `--live` делегирует `review_gate.run()`. Платный вызов делает только шлюз. Старый CLI сохранён и принимает `--pr-url`, `--approval`, `--state-dir`; скрипт по-прежнему спрашивает `Type REVIEW <sha>`. `make_prompt()` и `ask_argon()` остались для контракта PR #22 и помечены как offline-only: `make_prompt()` несёт весь diff и не ограничен 6 КиБ |
| 3 | средняя | **В пакете не было контекста проекта.** Argon получал hunks без истории репозитория и не мог отличить сознательное решение студии от ошибки | В пакете появился `project_context` (до 500 символов) рядом с `scope`, SHA, реальными hunks, тестами и ссылкой на PR. Значение по умолчанию — описание GremoVOD; `--project-context ""` убирает его |
| 4 | высокая | **Мост не мог отревьюить сам себя.** `tests/test_argon_review.py` содержал литерал вида `sk-` + `abcdefghijklmno123456`, записанный в одну строку. Сторож секретов считал это утечкой, и прогон против диффа этого репозитория падал с `BLOCKED / unsafe_diff` — то есть инструмент не мог проверить код, который сам реализует | Литерал собирается в рантайме (`'sk-' + 'abcdefghijklmno123456'`), поэтому в diff его больше нет, а тест по-прежнему ловит настоящую утечку. Добавлен `SelfReviewTest` — скан исходников и документов на секретоподобные литералы, чтобы дефект не вернулся. Заодно `test_argon_review.py` теперь импортирует `argon_review` обычным импортом, а не через `importlib`: иначе тест и шлюз держали два разных экземпляра модуля |

Симптом №4 стоит отдельной строки: он не проявлялся в юнит-тестах, потому что тесты
собирают фикстуры в рантайме. Он проявился только на **настоящем** диффе репозитория —
ровно тот случай, для которого инструмент и делается.

Побочный эффект усиления потолков: лимит «1 вызов на PR» теперь считается строго
по PR, а не по паре PR/SHA. После первого платного вызова по PR следующий запуск
на том же PR вернёт `BLOCKED / no_new_call`, даже если head SHA изменился.
Поднять этот потолок можно только правкой кода, которую владелец сначала прочитает.
Дневной (2) и недельный (5) лимиты при этом продолжают действовать.

## 5. Риски и что нужно от владельца

### Риски

1. **Цена неизвестна.** Пока тариф не подтверждён, `usd_amount` = `null` и верхняя оценка цены одного
   вызова задаётся владельцем через `ARGON_MAX_KIE_CREDITS_PER_CALL`. Без неё LIVE заблокирован — это
   осознанный fail-closed.
2. **Пакет неполный.** Argon видит до 4 файлов и критические hunks. Об остальном он не знает и может
   выдать `NEED_CONTEXT` или `UNSURE`. Это не дефект вердикта, а свойство экономии; `selection.partial_packet`
   сообщает об этом явно.
3. **Эвристика критичности.** Ранжирование hunks — детерминированная эвристика по имени файла и по
   опасным конструкциям в добавленных строках. Она может пропустить неочевидный, но дорогой дефект.
   Компенсация: `files_omitted` в пакете и в отчёте показывает, что не попало в ревью.
4. **Ложный PASS.** Argon PASS означает «в переданном hunks обоснованных дефектов не нашёл», а не
   «код корректен». В отчёте это зафиксировано строкой «Argon PASS is not a test PASS and is not a
   permission to merge».
5. **Баланс KIE — общий с другими инструментами.** `MIN_KIE_BALANCE` защищает от выхода в ноль, но
   другие потребители кредитов из того же аккаунта в баланс не видны.
6. **Файловое состояние.** Ledger, пакеты и слоты лежат в `%LOCALAPPDATA%\GremoVOD\argon-review`.
   Очистка этого каталога вручную обнулит счётчики — ledger'ом нужно пользоваться, а не удалять его.
   Слоты, оставшиеся от упавшего процесса, устаревают через 15 минут и перестают блокировать вызовы.

### Что нужно от владельца (в порядке важности)

1. **Числа кредитных лимитов** — `ARGON_MAX_KIE_CREDITS_PER_DAY`, `ARGON_MAX_KIE_CREDITS_PER_CALL`,
   `ARGON_MIN_KIE_BALANCE`. Без них LIVE не запустится.
2. **Разрешение на один проверочный запрос** по выбранному PR и SHA (этап B). Одобрение — файл
   `approval.json`, привязанный к SHA; новый коммит его гасит.
3. **Подтверждение тарифа** Argon, чтобы `usd_amount` перестал быть `null`.
4. **Решение по автоматике** (этап D): потолок «1 вызов на PR» стоит в коде. Для эскалации уровня B
   его нужно поднять правкой кода — не переменной окружения. По умолчанию остаётся 1, то есть ровно
   один платный вызов на PR.
5. **Решение по n8n Cloud** — только диспетчер/витрина, без ключей и без `Execute Command`.

вызов. Шаги — в `docs/ai-review/ARGON_KIE_MINIMAX_SETUP_RU.md`, раздел 5.
