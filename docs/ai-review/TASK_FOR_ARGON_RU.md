# Техническое задание для Gemini 4 Argon: оценить архитектуру Aider + GPT + Git

**Роль:** независимый read-only архитектурный ревьюер GremoVOD. Не изменять код и не выполнять команды. Подготовить задания для GPT, а не реализовывать их автоматически.

## Исходная идея пользователя

Исполнитель Aider + GPT разрабатывает локальный Windows проект; Git фиксирует изменения; Argon проверяет компактный diff и краткий контракт задачи; по итогам пользователю доступен понятный отчёт через GitHub PR. Цель — низкий расход токенов и минимальный риск конфликтов.

Предложены `git diff HEAD~1`, `--test-cmd python argon_review.py`, `--auto-test true`, `cache-prompts true`, `map-tokens 1024`, `max-chat-history-tokens 4000`, `edit-format diff`, авто-коммиты, `/clear`, `/drop`, браузер Aider и ungit.

## Известные ограничения (обязательно проверить)

1. Aider с GPT-6 Sol **уже работал** через KIE Proxy v2 на Windows (`localhost:8767`), маршруты GPT не трогать. GPT-6.1 Sol ещё не подтверждён в этой конфигурации.
2. У KIE Gemini 4 Argon официальный endpoint `https://api.kie.ai/gemini-4-argon-openai/v1/chat/completions`; провайдер предупреждает «chat only».
3. Репозиторий `C:\AI_Workflow_Studio` содержит `??`-файлы и отдельные наработки. До создания ветки изменения не трогать. GitHub repo: `gremoled77-droid/gremovod`.
4. В `--auto-test` не должно быть платных сетевых вызовов: риск циклов, ошибок 429, расходов и ложных исправлений.
5. `git diff HEAD~1` может не соответствовать конкретной задаче. Использовать `--base` и `--head`, фильтрацию бинарных/секретных файлов и проверку размера.
6. Не считать отсутствие замечаний Argon доказательством качества; после исправлений — локальные тесты и ручное подтверждение.
7. Prompt caching через нестандартный GPT/KIE-прокси пока не подтверждено; не обещать экономию в процентах.

## Что требуется предложить для GPT

- Архитектуру MVP с **ручным** запуском Argon после контролируемого Git-коммита, без прав на запись.
- Способы проверить безопасность: утечки секретов, состав diff, размер, бинарные файлы, обработка HTTP 429/5xx, тайм-аут и *отсутствие автоматических retry*.
- Сценарии аварий: пустой diff, первый коммит, невалидная ветка, несохранённые файлы, повреждённая кодировка Windows PowerShell, неверный JSON, отсутствующий KIE ключ.
- Команды Aider для отдельной ветки/worktree, бесплатных тестов и ручного просмотра результата в GitHub PR.
- Список замечаний P0–P3 и **конкретные задания GPT** с критериями приёмки; не предлагать ненужные рефакторинги.
- Как в будущем добавить ограничение циклов (максимум 1–2 ревью на задачу), остановку при бюджете и разделение «ошибка провайдера» / «код не прошёл ревью».

## Формат ответа

1. Подтверждённые риски в исходном подходе (с кратким обоснованием).
2. Рекомендуемый безопасный MVP.
3. ТЗ для GPT по шагам, от большего приоритета к меньшему.
4. Минимальные тесты приёмки, которые не обращаются к API.
5. Какие вопросы требуют отдельного LIVE-теста у KIE.

Без вызовов инструментов, без исполнения команд, без самостоятельного редактирования Git.
