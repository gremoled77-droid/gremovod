## 0. Как Codex получить материалы, если их ещё нет в main

**Это важно:** материалы Хукса пока в отдельной GitHub-ветке, а не обязательно в вашей рабочей ветке. Не предполагай, что они есть в `C:\AI_Workflow_Studio` после обычного запуска.

1. Открыть **своё** рабочее дерево: `C:\AI_Workflow_Studio\.worktrees\codex`, ожидаемая ветка `codex/work`; сначала сверить `git status --short`, `git branch --show-current`, `git worktree list`.
2. Прочитать локальные `AGENTS.md`, `CLAUDE.md`, `docs/HANDOFF_CLAUDE_CODE.md`, `docs/GIT_WORKFLOW.md`. При расхождениях актуальные ограничения окружения и сохранность данных приоритетнее этого ТЗ.
3. Выполнить `git fetch origin` в своём worktree и проверить `git status`. Не делать `reset --hard`, force-push, rebase чужой истории. При чистой рабочей ветке обновиться от `origin/main` по правилам `AGENTS.md`.
4. Убедиться, что существует `origin/docs/ed-hooks-acting-director-20261019`. Читать материал **даже если PR #10 ещё не объединён**, например:
   - `git show origin/docs/ed-hooks-acting-director-20261019:docs/CODEX_ACTING_DIRECTOR_HANDOFF_2026-10-19.md`
   - `git show origin/docs/ed-hooks-acting-director-20261019:docs/ED_HOOKS_ACTING_FOR_ANIMATORS_2026-10-19.md`
   - `git show origin/docs/ed-hooks-acting-director-20261019:skills/gremovod-acting-direction/SKILL.md`
5. До переноса документации в `codex/work` проверить `git diff --stat origin/main...origin/docs/ed-hooks-acting-director-20261019` и возможные пересечения. Можно аккуратно влить **документационную ветку в свою рабочую** после проверки статуса и диффа; **не** сливать её автоматически в `main` и не перетирать свежие изменения Claude. Если PR уже объединён, читать файлы из актуальной `main`, второй раз не вливать ветку.

Не править корневую рабочую копию на `main`. Основной стенд `8000/5173` трогает только Claude Code; Codex может тестировать на `8001/5174` со своим `STUDIO_DATA_DIR`. Не использовать реальную SQLite/медиа в тестах.

## 3. Предлагаемый пользовательский результат — минимальный вертикальный срез

**Место в продукте:** рядом со сценой/шотом на странице **«Раскадровка»**, без девятой страницы и без нового отдельного сценарного редактора. Сценарий сохраняется как исходный; Acting Sheet — **редактируемый постановочный слой**.

При открытии существующей сцены пользователь получает панель «Актёрская задача» / `Actor Beat Sheet`:
1. Выбирает героя из участников **этой сцены** (existing character IDs), при необходимости указывает партнёра. Не создавать героев из воздуха.
2. Видит и редактирует список смысловых битов в установленном порядке. Каждый бит — отдельная попытка героя повлиять на ситуацию, **не кадр и не реплика**.
3. В каждом бите — короткие поля: цель, действие/тактика, препятствие/собственная цель партнёра, замеченный триггер, реакция, новая тактика, **одно главное наблюдаемое действие**; необязательные заметки о слушании, телесном центре, плане/паузе и привязке к существующему шоту.
4. Выбирает статус заметки: **черновик/интерпретация/утверждено**. Автоматически не повышать до утверждено, не писать новые черты в канон Character Vault.
5. Может сохранить, снова открыть без потери данных, исправить отдельный бит и увидеть предупреждение о конфликте ревизий.
6. Получает «Режиссёрскую памятку / инструкция для видео» по выбранному биту: описание только **исполняемых** действий актёра. Отдельно поле для камеры, без принудительного изменения видеопромпта и без старта генерации.
7. Может скрыть панель и продолжить старый процесс без изменения рабочих данных; старые серии без Actor Beats функционируют как раньше.

**Решение после аудита:** предпочтительна отдельная сериализация по стабильной паре production/node + версия/ревизия (подобно `story_plan` или `visual_plan`). Не помещать автоматически весь Actor Beat Sheet внутрь `notes` сцены или общего `production_entity_state`, если это может вызвать разрушительные конфликты с уже работающей логикой. Схему поля и конкретную таблицу выбрать **после чтения кода и тестов**, обосновать решение в отчёте.

**Строго отделить три понятия:**
- `actor_beat`: смысловое изменение в актёрском действии;
- `storyboard frame/shot`: монтажный план, уже имеющий ID;
- `image/video keyframe`: технический референс/фаза, создаваемая только при необходимости выбранной модели.

Один actor beat может охватывать несколько шотов, один шот может иметь несколько битов; необязательные связи с кадрами не заставляют создавать новые кадры.

## 4. Предлагаемая форма данных — **не приказ изменить существующий API**

Ниже концептуальные поля. Перед внедрением решить, какие вообще нужны P0, какие оставить необязательными, проверить реальную схему и правила валидации:

```text
ActingSheet (proposed):
 production_id + series_id + scene_node_id
 revision / last_modified
 beats: [
  {
   id, order,
   performer_character_node_id,
   partner_character_node_id?, shot_node_ids?: [],
   objective, tactic, obstacle, partner_objective?,
   trigger, reaction, next_tactic?,
   visible_action, listener_action?,
   body_note?, camera_note?,
   status: draft | interpretation | approved
  }
 ]
```

**Ключевые гарантии:**
- все `character_node_id`, `scene_node_id`, `shot_node_ids` действительно принадлежат указанным проекту/серии/сцене;
- `id` и связи стабильны при перестановке, переименовании, новом дубле и повторном сохранении;
- нет кросс-проектных ссылок, дублирования битов, `NaN` / некорректных типов, бесконтрольной длины полей, XSS в тексте;
- нет записи ни в `character canon`, ни в оригинальные реплики; источник и статус ясно различаются;
- optimistic concurrency / revision conflict, 409 и сохранённый локальный черновик при устаревшей версии;
- удаление/архивирование сцены не должно неожиданно испортить другие серии; проверить текущие принципы cleanup и foreign keys;
- источник данных и приоритеты при чтении известны: `approved` не переписывает всё прошлое задним числом; `interpretation` не выдаётся за факт.

**API (условные действия, окончательные пути выбирает Codex):** чтение листа сцены, revision-safe сохранение, получение короткой текстовой режиссёрской инструкции из бита, при необходимости явное утверждение версии. Не вводить отдельную платную AI-кнопку в P0. Для начального выпуска допускается локальная **детерминированная** сборка инструкции из сохранённых полей без LLM.

## 5. Взаимодействие с моделями и агентами — что делать по этапам

**P0 сейчас:** пользователь **вручную** вводит/исправляет Actor Beats, сохраняет с привязкой к персонажу и сцене, получает черновую исполнимую постановочную инструкцию. Это проверяется на локальных фикстурах без внешних вызовов.

**P1 после работоспособного P0:** возможность безопасно передать выбранный `visible_action`, `trigger`, `reaction` и установленные ограничения в существующий prompt flow. Схема: `смысловая задача (для человека) → наблюдаемое действие (для видео) → модельный адаптер (с его разрешёнными параметрами)`. Не превращать «он обретает глубокую уверенность» в исполнимый промпт, не отправлять туда личностные домыслы.

**Важное условие:** если LLM-подсказка появится позднее, она выдаёт **кандидата**, не утверждённый бит. Требуются preview, одобрение пользователя и цена/подтверждение по существующей системе `GenerationReview`/`llm_guard`. Текстовый парсер/QA не должен запускать платный запрос, рендер или озвучку.

**Acting QA P0/P1:** сначала это объяснимые диагностические проверки **данных и связей**:
- есть ли цель и исполнимое действие (не одна эмоция);
- указан ли триггер, если изменяется тактика;
- есть ли самостоятельный ответ партнёра там, где на нём держится сцена;
- не исчезла ли реакция слушателя из плана;
- не навязана ли новая биография/новый реквизит/несогласованная характеристика;
- не перепутан ли бит с отдельным шотом;
- не смешана ли режиссёрская команда и команда камере;
- верны ли ссылки, статусы и версионность.

**После реального просмотра** клипа возможны отдельные записи `reviewed`/`observed_issue`, но никогда не ставить их за один проход текстового валидатора.

## 6. Примеры тестового материала (не сценарии и не канон)

### A. Грэм — первые кадры пилота, «раскрытие машины»
**Утверждённый постановочный принцип:** до завершения фразы диктора зрителю показывают Грэма за рулём, классические узнаваемые детали ВАЗ-2106 и дорогу в аэропорт, **без раскрытия удлинения и ключевых тюнингов**. После фразы — эффектный общий вид лимузина. Нельзя случайно показать тюнинг на раннем плане.

**Гипотеза по Хуксу:** Грэм серьёзен и уверен в VIP-качестве собственного автомобиля, не шутит над ним. Сцена на уровне актёрства может быть спокойной, контраст создаёт **информация зрителя**. В P0 фиксируем только эту задачу, не дописываем за владельца финальную фразу диктора, новые детали кузова, новые мизансцены и реплики.

**Тест:** сохраняемый бит и его экспорт не раскрывают ранние секреты кадра, не меняют текст диктора/дизайн машины и не добавляют новых шотов. Если источник канона отсутствует локально, использовать вымышленный аналог без настоящих ассетов.

### B. Грэм и гость — «сомнение в трансфере»
**Гипотеза:** Грэм старается убедить, слышит скепсис, меняет тактику на демонстрацию; гость самостоятельно выбирает доверять или нет. **Тест:** смена тактики имеет триггер; в инструкции для модели видимая реакция, не абстрактная «гордость».

### C. Катя — «контраст без гримас»
**Гипотеза:** осторожное, экономное движение и пауза могут контрастировать с экспрессией Грэма. **Тест:** статичность не помечается автоматически как «отсутствие актёрства», а предложенная манера не становится постоянным каноном.

### D. Ментальный наставник — «мудрость через экспрессию»
**Утверждён принцип:** эмоциональная экспрессия имеет цель — показать Грэму ошибку/самообман. **Тест:** постановочное действие связано с желанием повлиять на Грэма, а не «кричать для веселья»; не заявлять подтверждённого родства.

### E. Технические негативные случаи
Чужой `scene_id`/`character_id`; дубликат `beat.id`; stale revision; попытка сохранить `approved` без действия владельца; откат редактирования; независимые сцены в двух проектах; пустой Actor Sheet для старого проекта; нет источника видео или платных ключей.

## 8. Критерии готовности P0 (Definition of Done)

- [ ] Рабочая форма **на реальных сущностях сцены**, не только текстовый прототип.
- [ ] Можно создать 2–3 смысловых бита, сохранить, закрыть панель, открыть снова, отредактировать и сохранить.
- [ ] Есть явная связь с реальными ID сцены/актёра; кросс-проектные ID запрещены, ссылки на шоты только валидные.
- [ ] Исходный сценарий, канонические характеры, референсы и selected media **не изменяются** от редактирования Acting Sheet.
- [ ] Существующие сцены без acting-данных продолжают открываться; отсутствие данных корректно трактуется как пустой лист.
- [ ] Сохранение по устаревшей ревизии не теряет черновик, ошибка понятна.
- [ ] В тексте и UI явно разделены **«предложено»** и **«утверждено»**.
- [ ] Есть человекочитаемый экспорт актёрской задачи + конкретного действия, без платных генераций.
- [ ] Нет дублирования схемы сцен, не добавлено обязательное число битов, жестов, секунд или keyframes.
- [ ] Backend unit tests, frontend tests/build выполнены; неуспешное/непроверенное честно отмечено.
- [ ] Без ключей, реальных баз, медиа и исходного PDF в Git; без случайного автозапуска LLM/video/TTS.
- [ ] Codex сдаёт коммит, PR/ссылку на свою ветку и итоговый handoff.
