# Запуск студии в облаке и доступ с телефона

Студия остаётся локальной по умолчанию. Удалённый доступ включается только переменными окружения.

## Что нужно
- Сервер (VPS) с Docker и Docker Compose, открытые порты 80 и 443.
- Домен, A-запись которого указывает на сервер. HTTPS-сертификат выпустит Caddy сам.

## Шаги
1. Скопируй проект на сервер (без файлов `*_API_KEY.txt` и без `.venv`, `node_modules`).
2. `cp .env.cloud.example .env.cloud` и заполни: домен, `STUDIO_ACCESS_PASSWORD` (12+ символов), `PIAPI_API_KEY`.
3. `docker compose up -d --build`
4. Открой `https://<домен>/login` на телефоне, введи пароль. Сессия действует 14 дней.

## Как это защищено
- Без `STUDIO_REMOTE_HOSTS` любой запрос с чужим именем хоста отклоняется (403), как и раньше.
- Снаружи каждый запрос требует подписанную cookie входа; 5 неверных паролей с одного адреса блокируют вход на 5 минут.
- Cookie `HttpOnly`, `Secure` (за HTTPS), `SameSite=Lax`. Пароль и ключи живут только в окружении сервера.
- Платные запуски по-прежнему требуют оценки, подтверждения и лимита; серверные бюджеты проекта и дня действуют и в облаке.
- Все данные (база, библиотека, проекты) лежат в томе `studio-data`. Копия: `docker run --rm -v studio-data:/d -v $PWD:/b alpine tar czf /b/studio-backup.tgz -C /d .`

## Ограничение попыток входа и обратный proxy

Лимит попыток входа считается по адресу **прямого соединения**. Заголовок `X-Forwarded-For`
клиент подделывает сам, поэтому как идентификатор он не используется: раньше это позволяло
обходить лимит, подставляя новый адрес в каждый запрос.

Если перед студией стоит обратный proxy (в `docker-compose.yml` это Caddy), его адрес нужно
объявить доверенным — иначе все, кто заходит через один proxy, делят один лимит
(5 неверных паролей от кого угодно блокируют вход всем на 5 минут):

```
STUDIO_TRUSTED_PROXIES=172.18.0.3     # адрес контейнера caddy в docker-сети
STUDIO_TRUSTED_PROXY_HOPS=1            # один proxy между клиентом и студией
```

Правила, которые должны выполняться при такой настройке:

- В список доверенных попадает **только** адрес своего proxy (или его подсеть), а не вся
  приватная сеть: кто угодно с этого адреса сможет назвать себя любым клиентом.
- `STUDIO_TRUSTED_PROXY_HOPS` — число proxy между клиентом и студией. При значении 1
  берётся последний адрес в `X-Forwarded-For` (то, что записал ближайший proxy); всё,
  что дописал клиент слева, игнорируется. По умолчанию берётся столько ходов, сколько
  адресов в `STUDIO_TRUSTED_PROXIES`, — если в списке адресов больше, чем proxy на
  реальном пути, задай `STUDIO_TRUSTED_PROXY_HOPS` явно, иначе цепочка окажется
  «короче ходов» и лимит посчитается по адресу proxy.
- Доверенный proxy обязан сам записать свой адрес в `X-Forwarded-For` (заменить или
  дописать). Caddy это делает: входящие значения `X-Forwarded-*` он по умолчанию
  игнорирует, чтобы их нельзя было подделать.
- Если цепочка короче, чем `STUDIO_TRUSTED_PROXY_HOPS`, или в ней нет корректного адреса,
  лимит считается по адресу proxy — это не даёт подделать идентификатор клиента.

Без этих переменных поведение остаётся безопасным, но общим: все клиенты за одним proxy
делят один счётчик неудачных попыток.

## Что не проверено
Файлы `Dockerfile`, `docker-compose.yml` и `Caddyfile` написаны, но образ не собирался в среде разработки (там нет Docker). При первой сборке на сервере возможны мелкие правки.
Вход, cookie, ограничение попыток и проверка хостов покрыты тестами (`backend/test_remote_access.py`).

Доверенный proxy для лимита попыток входа (`STUDIO_TRUSTED_PROXIES`, `STUDIO_TRUSTED_PROXY_HOPS`)
на реальном сервере **не настраивался**: адрес контейнера caddy в docker-сети заранее неизвестен.
Пока переменные не заданы, все клиенты за Caddy делят один счётчик неудачных попыток — это
безопасно, но неудобно. Значения нужно задать владельцем перед удалённым использованием.
