# Независимое ревью денежного пути GA-01 (голова R3) и политика сверки нечитаемой суммы

- Объект: цепочка PR #58 → #76 → #79. Проверенная голова `784ea0c` (`build/claude/ga-01-r3-unreadable-barrier`), база `mavis/work` `57cac59`.
- Ревьюер: Claude Code, отдельная сессия. Код GA-01 не менялся: в этой папке только отчёт, пробы и скрипт проверки «только чтение».
- Без merge, платных вызовов, сети к провайдерам, ключей и рабочей SQLite. Все базы временные.
- Приёмка GA-01 владельцем здесь не заявляется. GA-02 не начинать.

## Вердикт

**Денежный барьер GA-01 можно принимать, но с одним условием (O1).** Барьер fail-closed, обхода бюджета не нашёл. R1–R5 и P1-A…P2-A закрыты, R3 убрал 500 и «ложный ноль» в экономике.

Блокер приёмки один, O1: при каждом старте студия сама переписывает денежные строки рабочей базы. Бэкапа нет, исходные значения нигде не сохраняются. Снять блокер можно двумя способами:

- **правка, рекомендую:** вынести `repair_legacy_money` из старта в отдельную команду с `--dry-run`/`--apply` и бэкапом, как уже сделано в `scripts/p0_migrate.py`;
- **условие без правки:** перед первым стартом после слияния владелец делает копию базы и прогоняет `tests/llm_ledger_dryrun.py`. Если скрипт показывает 0 строк под ремонт, ремонт на рабочей базе ничего не изменит.

Остальные находки (O2–O6) не блокируют. Их лучше закрыть вместе с политикой сверки, см. раздел ниже.

## Политика ручной сверки нечитаемой суммы

### Факты, на которые опираются варианты

1. Нечитаемая сумма появляется только из испорченных старых строк. Новый код её не создаёт. Есть ли такие строки в рабочей базе, неизвестно (NOT_RUN). Колонка `usd REAL NOT NULL`, и код всегда писал числа, поэтому вероятнее всего таких строк **0**. Проверить это даёт `tests/llm_ledger_dryrun.py`.
2. Сейчас такая строка останавливает траты своего проекта навсегда, а если создана сегодня, то и всех проектов. Сверка её не принимает, интерфейса сверки нет вообще.
3. Наибольшая оценка одного вызова при текущих потолках кода: чат $0.0624 (`gpt-6-astra`, 30 000 символов, 2 000 токенов выхода), задание MiniMax $0.0069. У прогона агентов (3 роли) резерв ограничен только `max_cost_usd ≤ $100`, потому что поля `character`/`style` без лимита длины. **Доказуемого потолка из кода нет**, любое число — решение владельца. Лимиты по умолчанию: проект $1, день $2.

### Варианты

| | A. Сумму называет владелец | B. Консервативный потолок | C. Списать в ноль с подписью владельца |
|---|---|---|---|
| Что происходит со строкой | остаётся нечитаемой и блокирует проект, пока владелец не введёт сумму из кабинета провайдера (`done` + сумма) или не подтвердит «списаний нет» с причиной | разовой командой с бэкапом получает `usd = потолок`, `submission_unknown`, `confirmed_usd=0`, исходное значение уходит в журнал. Дальше это обычная неопределённая строка и обычная сверка | владелец ставит `failed`/0 с причиной |
| Честность учёта | полная: число не выдумывается | число — политика, но оно удерживает деньги, а не освобождает | нарушает «неизвестное ≠ не потрачено». Для бывших `done` просто неверно |
| Простой проекта | до действия владельца | нет, если потолок помещается в лимит проекта | нет |
| Новый код | особый маршрут или режим сверки для `unreadable`, права «только владелец», UI | команда обслуживания (по образцу `p0_migrate.py`) и одно число. Особый маркер в колонке денег больше не нужен, и обработку `unreadable` в `spend_ledger`/`economics`/`series_economics`/будущем UI можно не множить | почти ничего |
| Риск | владелец не сопоставит строку со счётом провайдера, и проект стоит | реальное списание старой строки окажется выше потолка: занижен остаток лимита, но строка явно помечена неопределённой | экономика занижена, нарушено ТЗ |

### Рекомендация: B как переходное состояние, затем A как решение (B → A)

Потолок снимает простой и убирает особый маркер. Окончательную сумму по-прежнему называет владелец через уже существующий контракт сверки: `done` требует названную сумму, иначе 422. Вариант C не рекомендую. Он допустим только если кабинет провайдера доказывает отсутствие списания, а это уже вариант A с суммой 0.

Порядок:

1. **Сначала данные.** Владелец снимает копию рабочей базы и запускает `tests/llm_ledger_dryrun.py`, команды ниже. Если строк «станет unreadable» 0, вопрос о политике для существующих данных снят. Тогда достаточно O1, а нынешний fail-closed барьер остаётся страховкой.
2. **Ремонт только явной командой** с `--dry-run`/`--apply`, бэкапом и журналом исходных `usd`/`status`/`estimated_usd`. На старте остаётся только добавляющая миграция `confirmed_usd`: она пишет в новую колонку и не трогает существующие суммы. Это закрывает O1 и O2.
3. **Потолок утверждает владелец.** Предлагаю $0.25 за строку: выше любой оценки чата и MiniMax при нынешних потолках. Если в журнале есть оценки больше, взять наибольшую оценку той же модели: скрипт её печатает.
4. **Сверка:** только владелец (связано с `OWNER_AUTH_REQUIRED`), заметка дописывается, а не заменяется (`append_note` уже есть), нужен журнал ручных решений «было → стало». Для бывших `done` исход `failed` запрещён. Это закрывает O4.
5. **Тем же решением закрыть O5:** при старте одиночного процесса каждая строка `reserved` осиротела, её стоит переводить в `submission_unknown` с заметкой «процесс прервался во время вызова». Тогда она видна в «ждут сверки» и сверяется.
6. Кнопка «Сверить» в `BudgetPanel` (P2, можно позже). Пока сверка возможна только через API.

## Ответы на открытые решения из ретеста #77 и handoff MiniMax

- **Исход `done` подтверждает всю удержанную сумму.** Нынешний контракт верный: без названной суммы 422, названная сумма становится фактом. Частичное подтверждение оставило бы строку в `submission_unknown` навсегда, то есть добавило бы ручной работы. Рекомендую оставить.
- **Сегодняшняя нечитаемая строка останавливает траты всех проектов.** Рекомендую принять. Новый код такую строку не создаёт, на практике вопрос почти пустой.
- **Формат маркера `'unreadable'` в колонке `usd`.** При варианте B он больше не нужен. При варианте A его надо оставить и обработать O6.

## Решения владельца

1. Как снять O1: правка (вынести ремонт в команду с бэкапом, рекомендую) или условие (копия базы и dry-run перед первым стартом после слияния).
2. Политика нечитаемой суммы: B → A (рекомендую), A или C. Если B, утвердить число потолка.
3. Кто вправе сверять и снимать резерв: только владелец? Вопрос связан с `OWNER_AUTH_REQUIRED`.
4. Автоматический перевод осиротевших `reserved` в `submission_unknown` при старте (O5): да или нет.

## Как воспроизвести

Пробы (Linux, временные базы; `PYTHONPATH` указывает на рабочую копию `784ea0c`):

```
git worktree add --detach ../ga01-r3 784ea0c
cd ../ga01-r3
STUDIO_DATA_DIR=$(mktemp -d) PYTHONPATH=$PWD python -m pytest -q -s <путь>/tests/probe_opus_ga01.py <путь>/tests/probe_opus_barrier_without_repair.py
```

Проверку «только чтение» запускает владелец на своей машине (Windows). Рабочая база не открывается на запись: снимается копия через backup API, скрипт открывает копию в режиме `mode=ro`.

```
cd C:\AI_Workflow_Studio
.\.venv\Scripts\python.exe -c "import sqlite3; s=sqlite3.connect('file:studio.sqlite3?mode=ro', uri=True); d=sqlite3.connect('runtime/llm-audit-copy.sqlite3'); s.backup(d); d.close(); s.close()"
.\.venv\Scripts\python.exe -I <путь>\tests\llm_ledger_dryrun.py runtime\llm-audit-copy.sqlite3
```

`runtime/` в `.gitignore`, копия в Git не попадёт. Прогноз скрипта сверен с настоящим `repair_legacy_money` на синтетической базе: совпал по всем строкам, хэш файла после запуска не изменился.
