# Аудит по документу «GremoVOD Figma/CozyClay» и принятые решения

Источник аудита: `GremoVOD_FIGMA_COZYCLAY_COURSE_AUDIT_2026-10-27.md`
(приложен владельцем 27.10.2026). Документ описывает целевую архитектуру v0.5
(GremoVOD Studio) и требования к улучшению проекта.

Здесь — сверка требований документа с **реальным кодом** (ветка `codex/work`
после слияния с `origin/main`) и решения: что берём, что откладываем, что
отклоняем.

## 2. Принятые решения

**Р1. `ShotPlan` из документа не создаём — это мой `ShotContract`.**
Документ предлагает сущность «план кадра: действие, длительность, персонажи,
локация, расстановка, камера, свет, объектив, движение, previz-ссылки,
ключевые кадры», существующую **до** платного вызова и не зависящую от
провайдера. `ShotContract` уже отвечает этому требованию: контракт хранится в
студии, проверяется на непрерывность, утверждается человеком и не привязан к
модели. Вторая сущность с тем же смыслом создала бы два источника правды.
Решение: развивать `ShotContract` (правило добавления полей уже зафиксировано в
`SHOT_CONTRACT_V1.md`), а не плодить сущности.

**Р2. Реестр возможностей — источник истины для UI (инкремент №3, сделан).**
Требование «не хардкод: модель → возможности, цена, лимиты» и «выбор
first/last-frame недоступен неподдерживающей модели» закрыты новым модулем
`capability.py`. Факты взяты из уже разобранной документации репозитория
(`docs/VIDEO_MODELS_PROMPTING_2026-10-17.md`, `skills/video-*`), каждый со
ссылкой на источник; чего в источнике нет — не подтверждено (fail-closed).

**Р3. CozyClay — только read-only spike, не интеграция.**
CozyClay — AGPL-3.0-or-later. Встраивание в студию сделало бы её производной
работой с соответствующими обязательствами. Разрешён запуск отдельным
инструментом для сравнения раскладок, без кода в студии и без коммерческого
использования. Не блокирует MVP.

**Р4. Figma MCP / Figma Weave — внешний источник референсов, не хранилище.**
В студию не встраиваем. Референсы из Figma идут существующим каналом
(`reference_upload.py`, `public_references`) — он уже есть и работает.

**Р5. Иерархию «Сериал→Сезон» не расширяем сейчас.**
Добавление вида `season` меняет модель данных, навигацию и правила доступа к
производствам. Спрос на несколько сезонов не подтверждён, а цена — высокая.
Решение: оставить `project → production → series → episode → frame`. Если
потребность подтвердится — отдельной миграцией с тестами на перенос данных.

**Р6. Отдельную сущность `MediaAsset` не заводим.**
Таблица `library_assets` уже есть и связана с работами, файлами и галереей.
Новая сущность продублировала бы её. Правильный путь — расширить
`library_assets` полями происхождения (`origin`, `source_refs`,
`prompt_version`, `status`) миграцией, а не созданием второй таблицы. Это
отдельный инкремент: он требует миграции данных и политики хранения файлов.

**Р7. TTL 48 ч и корзина 7 дней — отдельный инкремент после Р6.**
Сроки хранения — продуктовое и юридическое решение (что именно «черновик»,
когда файл удаляется с диска, что делать с зависимыми ссылками). Реализовывать
до решения владельца опасно: можно потерять оплаченные результаты.

**Р8. Timeline (монтажка) и экспорт OTIO — следующий крупный инкремент.**
Это самая большая дыра из документа: сейчас монтажа как сущности нет вообще.
Порядок предлагаю такой: сначала **экспорт** того, что уже есть (шоты с
таймкодами → минимальный OTIO + `manifest.json` + media package без
абсолютных путей), потом **timeline-сущность** с треками. Экспорт проверяем
тестом, таймлайн — продуктовая развилка, где нужно решение владельца: студия
становится монтажным редактором или только отдаёт материал в Resolve.

**Р9. Навигацию не переделываем.**
Восемь этапов и десять инструментов уже есть (`StageNav.tsx`), рабочий
контекст сохраняется. Требование документа про переработку навигации — это
переформулировка того, что уже сделано, а не новая работа.

**Р10. Vision-QC по картинке — P1, отдельно.**
Требование «контракт сверяется с картинкой» требует модели зрения и платных
вызовов. В P0 не входит: платные вызовы без согласования цены запрещены.

## 4. Что дальше — по приоритету

1. **Интерфейс видеоэтапа** берёт режимы из `available_modes` и не даёт выбрать
   first/last-frame у модели, которая их не подтверждает. Маршрут готов,
   потребитель — этап «Видео» (`PromptStartMenu`, `frame_composition`) — это
   общая territory main, поэтому здесь только предложение.
2. **Экспорт**: минимальный OTIO + `manifest.json` + media package из шотов
   с таймкодами, без абсолютных путей, с честным статусом проверки импорта в
   Resolve (`passed / failed / not tested`).
3. **Происхождение ассетов** (`origin`/`source_refs`/`prompt_version`) —
   миграция `library_assets`, без новой таблицы.
4. **Timeline-сущность** — после решения владельца по Р8.
5. **Vision-QC** — P1, только после согласования цены.

## 5. Что документ не покрывает и стоит учесть

- В документе смешаны два слоя: продуктовая архитектура v0.5 и требования к
  качеству промптов. Второе в студии уже закрыто скиллами `skills/cinema-*`,
  `skills/video-*` и `backend/prompt_rules.py` — дублировать не нужно.
- Требование «не запускать неуспешный платный запрос» в студии реализовано
  двумя независимыми механизмами: оценкой и подтверждением
  (`llm_guard.py`, `generation_approvals`) и fail-closed выбором режима по
  профилю. Оба должны сработать до запроса — сейчас это гарантируется только
  для второго.
- Документ требует помечать проверку импорта в Resolve как `passed / failed /
  not tested`. Это правило фиксируем для экспорта: никаких «прошло» без прогона.
