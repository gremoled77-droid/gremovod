# Правила непрерывности, событий и флешбеков

Проверяется **текстовое состояние**, а не картинка. Vision-QC кадра в P0 нет и
не обещается: правила ниже ловят расхождения в замысле, которые человек может
увидеть глазами. Итоговое решение по кадру принимает человек.

Реализация: `backend/director_contracts/event_ledger.py` и
`backend/director_contracts/continuity.py`. Проверки: `backend/test_director_contracts.py`,
`backend/test_director_studio.py`.

## 1. Реестр предикатов

Свойства предметов описаны не абзацем, а парой «предмет + предикат». Список
предикатов закрыт на уровне модели (`PREDICATES`), расширяется миграцией.

| Предикат | Что означает |
|---|---|
| `vehicle_pose` | положение автомобиля |
| `door_state` | состояние двери |
| `vehicle_geometry` | геометрия кузова |
| `vehicle_color` | цвет кузова |
| `interior_exterior` | внутри или снаружи |
| `character_pose` | поза персонажа |
| `character_location` | где персонаж |
| `character_outfit` | одежда персонажа |
| `character_appearance` | внешность персонажа |
| `prop_held` | что в руках |
| `prop_contact` | с кем или чем контакт |
| `camera_position` | позиция камеры |
| `camera_framing` | кадр в кадре |

### Неизменяемые свойства

`LOCKED_PREDICATES = {vehicle_geometry, vehicle_color, character_appearance, character_outfit}`.

Это авторское решение, а не техническое ограничение: **удлинённый жёлтый
ВАЗ-2106 нельзя «перегенерировать» текстом** как автомобиль другой формы.
Смена такого свойства — ошибка, а не предупреждение. Список неизменяемых
свойств расширяется тем же способом, что и сам реестр.

> Расхождение с формулировкой ТЗ: в примере ТЗ предикат называется
> `position`. В коде он нормализован как `camera_position`, чтобы не спорить
> с `character_location`. Переименование выполняется миграцией реестра, а не
> правкой на лету.

## 2. Непрерывность внутри кадра

`check_continuity(shot)` проверяет один кадр:

1. **Предикат в реестре.** Неизвестный предикат — предупреждение
   `continuity_unknown_predicate`: работать можно, но свойство не проверяется.
2. **Переход что-то меняет.** Пустой переход (нет ни `from_value`, ни
   `to_value`) — ошибка `continuity_empty_transition`.
3. **Изменение обосновано событием.** Переход с `from_value` и `to_value`, у
   которого нет `event_id`, — ошибка `continuity_transition_without_event`.
4. **Неизменяемое не меняется.** `continuity_locked_change`, если
   `from_value != to_value` для предиката из `LOCKED_PREDICATES`.
5. **Конец кадра — это состояние после переходов.** Если один и тот же
   «предмет.предикат» есть и в `closing`, и в состоянии после переходов, их
   значения должны совпадать. Иначе — ошибка `continuity_value_mismatch` (или
   `continuity_locked_change` для неизменяемого свойства).

   Сравнение идёт именно с состоянием после переходов, а не с началом кадра:
   «дверь открылась в кадре» — это объявленный переход, а не расхождение.
   Ошибка означает обратное: переход открыл дверь, а в конце кадра она
   закрыта.
6. **Факт, который появился только в конце кадра,** — предупреждение
   `continuity_undeclared_closing`: изменение не объявлено переходом. Само по
   себе это не ошибка (факт мог появиться и без перехода), но режиссёр должен
   знать, что причина не зафиксирована.

## 3. Непрерывность между кадрами

`check_chain(shots)` сравнивает конец предыдущего кадра с началом следующего:

- состояние после кадра = `opening`, затем применённые `transitions`
  (`state_after`);
- если для пары «предмет.предикат» значения различаются и переход не был
  объявлен — ошибка `continuity_chain_break`;
- если предикат неизменяемый — `continuity_locked_change`.

Сравниваются только соседи **одной сцены**: между сценами состояние может
измениться законно.

## 4. Скачки времени и флешбеки

### Три режима непрерывности

| Режим | Что означает | Что происходит с проверками |
|---|---|---|
| `continuous` | кадр продолжает предыдущий | проверяется полностью |
| `time_jump` | между событиями прошло время | состояния до и после не сравниваются |
| `flashback` | показ прошлого | состояния до и после не сравниваются |

В режиме `time_jump` и `flashback` внутрикадровые правила 1–4 продолжают
работать (сам кадр всё равно должен быть непротиворечивым), но правило 5 и
сравнение с соседним кадром отключаются: разрыв объявлен автором.

### Два порядка

`presentation_order` — порядок показа зрителю, `timeline_order` — хронология.
Они расходятся в флешбеке: событие «открытие двери» может идти по хронологии
раньше, а показываться позже.

`FilmOrder` хранит оба порядка и список `TimeJump(before_event_id,
after_event_id, reason)`. Расхождение порядков **не является ошибкой** само по
себе — ошибкой считается расхождение без объявленного скачка времени.

### Что проверяется в реестре событий

| Код | Правило |
|---|---|
| `event_duplicate_id` | ID события не повторяется |
| `event_unknown_causal` | причина существует в реестре |
| `event_self_causal` | событие не является причиной самого себя |
| `event_causal_order` | причина идёт по хронологии не раньше следствия |
| `event_missing` | обязательное событие закреплено хотя бы за одним кадром |
| `event_covered_twice` | обязательное событие закреплено ровно за одним кадром |
| `event_unknown_shot` | ссылка ведёт на существующий кадр |
| `shot_unknown_event` | ссылка кадра ведёт на существующее событие |
| `event_id_unstable` | ранее известное событие не исчезло из реестра |
| `asset_unknown` | ссылка на ассет ведёт в библиотеку проекта |
| `continuity_undeclared_closing` | факт появился только в конце кадра, переход не объявлен |

Повторно показать событие можно, только если оно помечено `repeatable`.
Обычное авторское событие (`locked: true`) повторять нельзя.

## 5. Как замечания попадают в интерфейс

1. `validate_contracts(events, shots, assets)` собирает замечания из всех
   проверок и сортирует их детерминированно: сначала ошибки, затем
   предупреждения, внутри — по коду, потом по пути, потом по тексту. Один и
   тот же вход всегда даёт один и тот же список в одном порядке.
2. `Issue` — это код, серьёзность (`error` / `warning` / `info`), путь и текст.
3. В студии замечания разделяются на «по этому кадру» и «по серии в целом».
   Покрытие событий — свойство серии, поэтому не блокирует сохранение одного
   кадра, но видно в обзоре.
4. Контракт с ошибками сохраняется как `draft`: сначала правка, потом подпись.

## 6. Чего эти правила не делают

- Не сравнивают картинку с контрактом (vision-QC — P1).
- Не проверяют, существует ли ассет, по содержимому — только по ID в
  библиотеке проекта.
- Не оценивают качество кадра, композицию или соответствие режиссёрскому
  замыслу.
- Не заменяют решение человека: замечания — предупреждение, а не приговор.
