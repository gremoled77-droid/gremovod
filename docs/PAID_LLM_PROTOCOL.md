# Платный LLM: единый протокол и живая проверка Luna

Решение владельца от 20.10.2026: платный LLM включается, платные маршруты
приводятся к одному протоколу, Луна подключается по API.

## Один протокол на всех платных маршрутах

Раньше платных входов было три, и они различались по строгости:

| Маршрут | Было | Стало |
|---|---|---|
| `/api/llm/chat` | оценка → подпись → подтверждение → лимит → журнал | без изменений |
| `/api/compose` | прямой вызов без оценки, лимита и записи → **503** | тот же протокол, заморозка снята |
| `/api/agents/run` | N прямых вызовов без учёта → **503** | один резерв на прогон, N вызовов, одно списание по факту |

Схема везде одна:

```
оценка (estimate)  →  подпись (quote_token)  →  подтверждение (approved)
                    →  резерв в журнале расходов  →  вызов провайдера  →  списание по факту
```

Требования, которые проверяются на каждом маршруте:

1. **Оценка считается на сервере.** Клиент присылает модель и вход, сервер
   собирает сообщения сам и возвращает `estimated_usd` и `quote_token`.
   Фронтенд не считает цену сам — иначе подпись не совпадёт.
2. **Подпись привязана к тому, что реально уйдёт провайдеру.** Хэш сообщений и
   `max_tokens` входят в подпись; изменение входа ломает подпись (400).
3. **Подтверждение обязательно** (`approved: true`), и **лимит стоимости** не
   может быть ниже оценки.
4. **`request_id` обязателен** и защищает от повторной оплаты: повтор того же
   `request_id` даёт 409, второй вызов не выполняется.
5. **Резерв в журнале расходов создаётся до обращения к провайдеру**
   (`llm_guard.reserve_call`). Без резерва провайдер не зовётся вообще: точка
   выхода (`main.require_spend_reservation`) отклоняет запрос с 403.
6. **Списание — по факту.** Фактические токены считаются по ответу провайдера,
   оценка не потолок: превышение видно в журнале (`over_estimate`), а не
   прячется под оценкой.
7. **Исход неизвестен не прячется.** Отказ 4xx — провайдер не исполнил запрос,
   резерв освобождается (`failed`, 0). 5xx, таймаут, обрыв, неразобранный ответ —
   `submission_unknown`: деньги могли быть списаны, резерв держится до сверки.

## Выбор провайдера

`provider` в запросе больше не прибивает вендора:

- пустой `provider` — «возьми провайдера этой модели из реестра»
  (`model_catalog.llm_spec`);
- явный провайдер проверяется на совпадение с реестром, несовпадение — 400;
- `mock` — локальный режим без обращения к провайдеру.

Из интерфейса убран выбор провайдера: в списке был единственный пункт «PiAPI»,
и он же был хардкодом вендора в клиентском коде.

## Маршруты агентов: один резерв на прогон

Прогон агентов — это три последовательных платных вызова (директор,
непрерывность, промпт), и каждый следующий видит результаты предыдущих. Поэтому:

- оценка считает **все три роли** с запасом на растущий контекст
  (`AGENT_PREVIOUS_CHARS`), а не один вызов;
- в журнале расходов **одна запись** на весь прогон, а не три: резерв
  создаётся один, вызовы идут против него, списывается факт по сумме
  токенов всех ролей;
- обрыв на середине даёт `submission_unknown` с указанием, сколько ролей
  успело пройти: часть могла быть оплачена.

## Живая проверка: gpt-5.6-luna через API

Один реальный вызов через штатный путь студии (временная база, ключ из файла
провайдера в окружение; ключ в вывод не попадает):

```
ОЦЕНКА  200  estimated_usd = 0.000009
ВЫЗОВ   200  "Водит."  provider=piapi  model=gpt-5.6-luna
         usage: prompt 32, completion 35 (из них 25 reasoning)
         cost_usd = 0.000005, over_estimate = false
ЖУРНАЛ  request_id=luna-live-check-1  model=gpt-5.6-luna  status=done
         usd=0.000005  estimated_usd=0.000009
```

Проверено на живом провайдере: оценка, подпись, подтверждение, резерв, вызов,
списание по факту и запись в журнале. Повторная оплата при повторном
`request_id` не выполняется.

## Где граница оплаты

Не в списке замороженных маршрутов, а в точке выхода к провайдеру:
`backend/main.py::require_spend_reservation` → `security.spend_reserved`.
Любой новый платный маршрут, который не проходит через `guarded_chat` или
`llm_guard.reserve_call`, получит 403 на выходе — даже если забыт.

## Что сделано

| Файл | Что |
|---|---|
| `backend/llm_guard.py` | `resolve_provider`, `reserve_call`, `settle_call`; `guarded_chat` переведён на них и возвращает фактического провайдера |
| `backend/main.py` | `provider` необязателен в чате, compose и агентах; `/api/compose/preview` даёт оценку и подпись; `/api/agents/estimate` считает все роли; `/api/agents/run` — один резерв, N вызовов, одно списание |
| `backend/security.py` | снята заморозка `/api/compose` и `/api/agents/run` |
| `frontend/src/api.ts` | `PAID_LLM_ENABLED = true` |
| `frontend/src/paidProtocol.ts` | общий протокол: подпись, лимит, `request_id` — одно место на все компоненты |
| `frontend/src/App.tsx` | чат-панель: оценка → цена → подтверждение; провайдер из реестра; в провайдер уходит хвост истории (20 сообщений) |
| `frontend/src/AgentPanel.tsx` | оценка → подтверждение; плашка «платные агенты выключены» снята |
| `frontend/src/PromptComposer.tsx` | цена из оценки; плашка «резерв отключён» снята |
| `frontend/src/SettingsPanel.tsx` | выбор провайдера убран: его выбирает реестр |
| `frontend/src/IdeaBrief.tsx` | провайдер из реестра вместо хардкода `piapi` |

## Проверки

- `backend/test_llm_guard.py` — новые тесты: общий протокол на compose и
  агентах, оценка → вызов → запись в журнал, повтор `request_id` → 409 без
  второй оплаты, агентский прогон: три вызова провайдера и **одна** запись в
  журнале, отсутствие подтверждения или подписи → провайдер не зовётся.
- `backend/test_smoke.py` — заморозка 503 заменена проверкой отказа по
  протоколу.
- `frontend/paidProtocol.test.mjs` — тело платного запроса всегда несёт
  подпись, лимит и `request_id`.
- Красные прогоны зафиксированы и откачены: отключение проверки подписи
  (запрос без подписи проходил, 200 вместо 400), резерв на каждую роль вместо
  одного (4 записи вместо 1), потерянная подпись в теле запроса на фронтенде.
