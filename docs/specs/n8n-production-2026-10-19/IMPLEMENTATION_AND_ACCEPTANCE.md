# Реализация по этапам и приёмка

Статус всех работ ниже — план. Создание этого документа не означает выполнения тестов или разрешения платных запросов.

## 0. Обзор спецификации

- Получить обзор GPT Astra по REVIEW_GPT_ASTRA.md.
- Исправить найденные пропуски/циклы и зафиксировать решения по открытым вопросам.
- Утвердить границы первого реального пилота: одна небольшая сцена, обязательные модальности и формат файла.
- Не удалять этапы полной схемы ради быстрого текстового демо.

**Готово, когда:** для каждой операции есть входы, результат, критерии и восстановление, а нерешённые решения перечислены.

## 1. Видимый полный каркас без моделей

Реализовать основное полотно N01–N43 и общие сервисы как sub-workflow/группы. Физическое разбиение может быть компактнее каталога, но каждый логический узел виден и прослеживается. Новые узлы показывают NOT_IMPLEMENTED/BLOCKED, не выдают фиктивный PASS. Для тестовых ответов отдельный режим MOCK, в выходе всегда synthetic=true.

Создать минимальные контракты, журнал и граф версий/зависимостей. Первые проверки — только фиксированные ответы, локальные test assets и ноль provider submits.

**Готово, когда:** путь до Готовых нельзя пройти с пропущенным критиком, неподтверждённым финальным решением или новым hash; FAIL возвращает адресно; BLOCKED сохраняет checkpoint.

## 2. Реальная идея, варианты, сценарий

Подключить N01–N10, S01/S02/S04/S05/S07/S08/S09. Предварительно выбрать доступные текстовые модели, проверить профили, сметы и ограничить число вызовов. Использовать настоящее авторское задание и явно утверждённые правила, а не встроенную историю про тестовый цвет машины.

Проверить A0 → A1 варианты → выбор → сценарий → A6/A7; TEXT_CRAFT подключить отдельной согласованной реализацией, если обязателен политикой. Первое модельное исполнение только после конкретного бюджета. Плохой текст должен получить FAIL, исправленный — пройти по тем же критериям.

**Готово, когда:** есть сохранённый сценарий и вердикты нужной версии. Это не готовность медиа или финальной сдачи.

## 3. Режиссура, персонаж и локация

N11–N14: выбрать один образ персонажа, одну локацию и комплект ракурсов. Временно достаточно ручного манифеста. Проверить разные роли исходников и сохранение географии в карточках кадров, постановку реплик и зависимость от сценария.

**Готово, когда:** каждая карточка связана со сценой, репликами и конкретными файлами референсов; недостающее не скрывается. Новые канонические образы отдельно утверждены.

## 4. Одно изображение, затем набор кадров

N15–N19 и S03/S06: один проверенный image-провайдер, реальный исходник, промпт/параметры/стоимость в предпросмотре, сохранённый файл, критика по фактической картинке. Затем несколько кадров одной сцены.

**Готово, когда:** нарушение внешности/геометрии/действия обнаружено, исправление касается нужного кадра; старый дубль не потерян. Несовместимый параметр блокируется до submit.

## 5. Голоса, звук и тайминг

N20–N25: один доступный голосовой/аудиоинструмент. Проверить весь текст, смысловую сегментацию, произношение, подачу и фактическую длительность. Использование голоса/музыки должно быть разрешено в проекте.

**Готово, когда:** дорожки реально сохранены, речь прослушана и полна, A2 получает фактический тайминг. Один транскрипт не даёт PASS тембру.

## 6. Видео и исправление клипа

N26–N31: один видеоадаптер, выбранный keyframe, согласованный audio/native-audio путь, реальный клип. Проверить движение, дрейф лица/пространства, действие и при необходимости lip-sync. Native audio вариант выполняет аудиопроверку до монтажа.

**Готово, когда:** доступен весь обязательный coverage; конкретная проблема возвращается в кадр/промпт/тайминг, а не перегенерирует всю сцену автоматически.

## 7. Монтаж и итоговый файл

N32–N34: подключить реально доступный автоматический renderer/worker либо явно обозначенный ручной CapCut export в раннем пилоте. Ручной экспорт не объявлять полной автоматизацией.

**Готово, когда:** существует воспроизводимый master с известными исходниками/параметрами, полными репликами и просмотром/прослушиванием. Таймлайн/код не считается файлом.

## 8. Три финальных критика и решение автора

N35–N41: замороженный master, независимые A6/A7/A8, совпадающие хэши и достаточное наблюдение. Все три должны быть реально подключены и разрешены; A8 не включать без server-side approval и средств проверки. Затем человек смотрит файл и явно выбирает Готовые.

**Готово, когда:** три валидных PASS → только ожидание владельца; только его решение создаёт READY. Отказ возвращает на конкретный этап.

## 9. Полный приёмочный пилот и Studio

Пройти реальную сцену от идеи до готового файла. Намеренно внести один контролируемый дефект, проверить обнаружение, адресный возврат и новый финальный QA. Зафиксировать вызовы, расходы/неизвестные списания, время ожидания и ручные зависимости. Только после этого проектировать интерфейс Studio, автоматизировать библиотеки и выбирать дополнительные модели.

## Сквозная матрица испытаний

| Сценарий | Ожидаемое поведение |
|---|---|
| Неполная идея | A0 запрашивает существенное, не требует сценарий вместо идеи |
| Три одинаковых варианта | Критика отмечает отсутствие содержательного выбора |
| Изменён смысл реплики режиссёром | Возврат A1 и пересмотр зависимого текста/тайминга |
| Недоступный файл Windows из Cloud | BLOCKED, явная задача передачи файла, не фиктивный просмотр |
| Новый неутверждённый профиль персонажа | Candidate, запрос утверждения до использования как канона |
| Подмена лица/локации | FAIL с реальным визуальным evidence |
| Лишний параметр другого API | Блокировка до платного submit |
| Ручная правка промпта после approval | Новый hash и повторная проверка разрешения |
| Тег TTS попал в речь / потеряны слова | FAIL аудио, исправление сегмента |
| Кадры видео есть, звук недоступен | BLOCKED обязательного AUDIO, не общий PASS |
| Timeout после submit | UNKNOWN, сверка job, без повторного списания по инициативе системы |
| Дубликат callback или resume | Существующий job/result используется повторно |
| Устаревший ответ/другой проект | Ответ сохраняется отдельно, текущую версию не принимает |
| Достигнут предел раундов/денег | PAUSED до явного решения |
| Промежуточные PASS, финальный дефект | Финальные критики обнаруживают его независимо |
| Один критик FAIL или недоступен | Нет READY, никакого majority vote |
| Три PASS разных хэшей | BLOCKED как несовместимый пакет |
| Три PASS одного файла, человек не решил | AWAITING_OWNER_APPROVAL |
| Человек вернул титр | Правка титра/рендера, новые три финальных вердикта |
| Явное принятие того же hash | READY с проверенным файлом и manifest, без публикации |
| Повторное принятие | Идемпотентный результат, без дубля/потери исходников |
| Попытка обойти A8 текстовым отчётом | BLOCKED, реальные media evidence обязательны |

## Минимальная политика пилота

Предложение для утверждения: один автоматический цикл исправления на этап, отдельный общий денежный/временной предел. Значения валюты/цен не выдумывать: смета после выбора реальных подключений. Не обещать hard billing stop провайдера без проверки. Все LLM-вызовы, критики, транскрипция, обучение и media jobs включаются в расчёт, если платны.

N42 может возвращать только на разрешённые рабочие этапы: N03, N04, N05, N06, N08, N09, N11, N12, N13, N15, N20, N21, N26, N27, N32, N33. Прямой переход в N17/N23/N29 минуя preflight или в N40/N41 запрещён. Перед новым платным вызовом S04 применяется всегда.


## Принятые исправления плана после Astra (v1.1)

Вначале проверить изменённые P0/P1/P2 контракты по [ASTRA_FIXES_V1_1.md](ASTRA_FIXES_V1_1.md), [nodes.json](nodes.json), а также временные SQLite/offline tests. Код reference pilot не внедрён в рабочий API; Cloud и Windows не имеют безопасного соединения по факту появления файла.

В первой фазе допустим только **контролируемый MOCK**: полный логический реестр N01–N43/S01–S09, явные BLOCKED/NOT_IMPLEMENTED, 0 API вызовов, сценарии stale/UNKNOWN/budget/manifest/owner. Нельзя заменить этим настоящие SQL concurrency tests или paid provider tests.

Во второй фазе, **только после появления видео**, сначала испытать загрузку настоящего короткого MP4, хэш, video+audio+movement capabilities по известным дефектам, три независимых ролей на одном snapshot и ручную приёмку. До этого нельзя объявлять этапы 4–9 готовыми либо начинать дизайн Studio. Native audio и lip-sync пути отложены, но маршруты и разделение заявок уже зафиксированы.

Финальный критерий формулировать как «**реальный** материал → доставка → независимые проверяющие с фактическим coverage → адресное исправление → владелец», а не «все узлы зелёные». Границы бюджета и одобрения перед каждым платным submit обязательны.
