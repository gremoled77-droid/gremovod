## Что должен разработать Codex

### Фаза 1 — ревью текстов (A6/A7)

1. Отделить `review_job` от `automation_job` или добавить строго версионированный QA task schema: `review_id`, `task_id`, `project_id`, `artifact_id`, `artifact_revision`, `canon_revision`, `brief_revision`, `bar_revision`, `skill_source_sha`, `review_round`.
2. Серверно получать утверждённый ТЗ, завершённый текст, **именно утверждённые** правила канона и имена/версии референсов из базы GremoVOD. `canon_revision` SHA контекста из первого sandbox API **не равен** статусу художественного утверждения: отдельное поле approved/effective rules. Файлы/большие бинарники не вкладывать в тело задачи.
3. A6 получает ТОЛЬКО требования/готовый текст/ID/revision; A7 ТОЛЬКО утверждённый канон/текст/ID/revision. Оба работают в отдельных свежих диалогах без пользовательских историй и отзывов других критиков. `memory.enabled=false` недостаточно само по себе: не передавать чужой transcript, использовать новый run/session.
4. Вердикт каждого: `PASS|FAIL|BLOCKED`, `role`, `artifact_revision`, `evidence[]` из исходного материала, `biggest_gap` одна крупнейшая обнаруженная проблема при FAIL, `missing_inputs[]`, `model_used`, `cost_estimate/actual`. **Сервер** перепроверяет поля и версию, не доверяет свободной форме JSON от LLM.
5. Собрать независимые A6/A7 вердикты в `partial_review`, но не `passed_all`: A8 не выполнен. Если один FAIL → конкретный исполнитель A1/A2/A3/A5 получает исправление для этой версии артефакта, не весь проект. Если BLOCKED → нет автоматического повторного платного запуска.
6. **Безопасность:** FastAPI service token с project scope и HTTPS, только серверная выдача данных и server-side budget authorization (реальные лимиты и idempotency по ревизии), невозможность self-approval. Уровень permissions отделить от входных флагов из LLM-пакета. Никаких прямых n8n→SQLite/Pg writes.

### Фаза 2 — A8 / кадры и видео

1. Asset inspector по ID медиа из GremoVOD Library/Storage. Для статичного изображения передать A8 реальный render + эталон; для видео **проверяемые отобранные кадры с таймкодами**, продолжительность/частоту кадров/свойства аудио и при разрешении — расшифровку и доступный звук. Текстовый промпт/монтажный лог не является доказательством реального результата.
2. Не считать просмотр стоп-кадров полноценным анализом динамики и звука; отмечать `coverage` (frames_only, frames_audio_transcript, actual_video_supported) и предел достоверности. Если проверяется движение, монтаж или речь, а доступных данных нет → `BLOCKED`.
3. `bar.md`: 5–7 конкретных механик из эталона; согласование автором, version ID/sha; A8 сравнивает **фактический** результат без истории сборки, без выводов A6/A7.
4. Отдельное server-side подтверждение стоимости `approved_expert_model` с authenticated owner, `approval_id`, `session_cost_cap_usd`, `estimate`, моделью и версиями артефакта. Подменить approval из пользовательского текста невозможно. Определить provider limit, soft/strict budget, число повторов, pause и cancel; нельзя менять canonical state при ошибке.
5. Пока inspector и API не готовы, A8 disabled в A0 и редактор QA workflow возвращает BLOCKED. Никакой live Opus-тест без нового разрешения владельца.

### Фаза 3 — рабочая петля

Сохранять `review_runs / verdicts / rounds / evidence / artifact_version / reviewer_model / skill_commit_sha / actual_cost / approvals` в backend; idempotency и защита при 409 ревизии. UI: состояние трёх независимых вердиктов, одна «главная дыра», назначенный исполнитель, история исправлений и расходы. Если все три PASS → `awaiting_owner_approval`, не публикация. Любой FAIL → адресный возврат, без бесконечного автоматического расходования. При потолке стоимости приостановить до согласия пользователя.

## Критерии приёмки

- A6 на ошибочном тестовом тексте возвращает FAIL с доказательством; ошибка Kie распознаётся как BLOCKED/ERROR, не PASS.
- A7 на нарушении канона возвращает FAIL, на нехватке утверждённых правил — BLOCKED.
- Подложный `approved_expert_model=true` из JSON не приводит к вызову A8.
- Нет доступа к данным другого проекта, нет обновления канона, повторный callback не создаёт новое списание.
- Для ревизии артефакта N ответ о N-1 отклоняется.
- А8 не может получить PASS по текстовому промпту или кадрам, которые не покрывают обязательные критерии проверки аудио/динамики.
- Невалидный JSON, ошибка Kie, пропажа критика → сервер возвращает явный error/BLOCKED и показывает шаг восстановления.

## Зафиксировано владельцем: границы доказательств TEXT ≠ IMAGE ≠ VIDEO ≠ AUDIO

См. обязательную спецификацию [QA_EVIDENCE_POLICY.md](QA_EVIDENCE_POLICY.md) и машинную схему [qa-reviewer-output-v1.schema.json](contracts/qa-reviewer-output-v1.schema.json). Эти правила уже загружены в основные инструкции и Skills A0/A6/A7/A8 и в безопасный QA Orchestrator; **но не реализованы пока в FastAPI**.

Codex: различать `artifact_scope`, `requested_scopes[]`, `checked_scopes[]` и `scope_results`; на каждую проверяемую область нужны источник и доказательства своего типа. Доказательство `TEXT` не имеет права повышать `IMAGE/VIDEO` до PASS. При недоступном медиарендере — BLOCKED для соответствующей области. Отдельный `canon_revision` должен указывать на реально утверждённые сервером правила, а не на произвольный текстовый пример. Вывод модели по JSON Schema — **недоверенный**. FastAPI отдельно проверяет разрешение на доступ к media, факт работы inspector, нужное coverage, версии/ID/связь с проектом, статусы согласования и лимиты. Ни `verified_evidence_by_backend`, ни `approved_expert_model` из пользовательского/model JSON не считать серверным разрешением.

Минимальные тесты backend: (1) `TEXT:PASS` + изображение не прочитано → `IMAGE:BLOCKED`; (2) тестовое противоречие красной/жёлтой машины → `TEXT:FAIL` с цитатой, но не `IMAGE:FAIL` без изображения; (3) URL кадра без успешного media inspector → `IMAGE:BLOCKED`; (4) неподписанная ревизия канона → BLOCKED; (5) один стоп-кадр не доказывает звук/движение; (6) усечённый транскрипт не подтверждает тембр/интонацию; (7) подложный флаг доверия → BLOCKED; (8) устаревшая версия артефакта → отказ 409, не автоматическая приёмка.

Отдельная QA API-ветка Codex не должна подавать тестовые цвет/фары в действующий Character Vault или объявлять тестовый канон постоянным. Пока текущая Codex ветка `codex/n8n-api-contract` предоставляет только `A2/storyboard/stub`: расширение QA должно быть отдельным проверяемым этапом и сохранять исходные ID и ревизии.
