# GremoVOD — независимая продюсерская приёмка: петля трёх критиков

**Статус (19.10.2026):** A6–A8 созданы в n8n как unpublished draft, отдельный безопасный QA Orchestrator `nh3ARcl4XPW6RHqs` готовит три независимых пакета и агрегирует BLOCKED. Это **не действующая петля проверки**: нет вызовов LLM/медиа и разрешённых бюджетов. Два теста Code/Merge без оплаты успешны. Подробнее: [QA_ORCHESTRATOR_IMPLEMENTATION.md](QA_ORCHESTRATOR_IMPLEMENTATION.md). Основано на предоставленном владельцем документе «Дизайн-петля» (фазы: интервью → проверка готовности → разбор эталона → петля). Не заменяет основную схему этапов GremoVOD.

## Решение

**A0 / продюсер-координатор** завершает производство, инициирует финальную проверку и собирает вердикты, но **не оценивает собственную прежнюю работу**. Качество проверяют **три логически независимых критика с новым контекстом**. Это три специализированные роли/вызова, а не отдельный агент на каждый SKILL.md; на этапе реализации их можно оформить как три isolated subworkflow/Agent runs, затем решить, нужно ли хранить их как отдельные n8n Agents. Изоляция должна быть реальной: у критиков нет общего чата и истории построения, они не читают ход работы сборщика.

| Роль | Что получает | Что проверяет | Стартовая модель |
|---|---|---|---|
| REVIEW-REQ — КРИТИК ТЗ | исходный запрос, согласованные требования, готовый артефакт или проверяемую структуру | сделано ли то, что просил автор; **красоту игнорирует**; строгие критерии и полнота | Claude Haiku 5.5 |
| REVIEW-SYSTEM — КРИТИК СИСТЕМЫ | утверждённый канон/дизайн-система, выбранные референсы, итог | постоянство персонажа/машины, стиля, монтажа, правил проекта, объективные отклонения | Haiku 5.5 для однозначного; Sonnet для смысловых конфликтов |
| REVIEW-CRAFT — КРИТИК РЕМЕСЛА | рендер итогового кадра/клипа/серии, утверждённый `bar.md`, эталон; без истории генерации | сравнивает результат с эталоном, оценивает художественное исполнение **по видимому/слышимому**, называет **одну крупнейшую проблему** | Claude Opus 5.5 — **только после утверждения бюджета/защищённого approval** |

ТЗ в файле «Дизайн-петля» называет Критика Ремесла самой сильной моделью; **не понижать его модель ради экономии**. Если бюджет на Opus не разрешён, показывать `review_blocked/needs_approval`, а не ложно подтверждать качество дешёвым критиком.

## Фазы, как в источнике

1. **Интервью.** Собрать три обязательных элемента: **что делаем и объём/длительность**, **конкретный открываемый эталон**, **входные файлы** (сценарий, библия, референсы). Для существующего проекта заполнять из FastAPI/Character Vault без повторного опроса владельца. Если эталон расплывчат — уточнить один раз; если нет — предложить три конкретных варианта и дождаться выбора. До этого не начинать «петлю».
2. **Проверка готовности.** Удостовериться, что эталон и исходники доступны, рендер можно получить и посмотреть, нужные модели/инструменты действительно подключены. Доложить `works/missing/blind_critic`. **Нет визуального/аудиодоступа — Критик Ремесла не может выставить PASS**.
3. **Разбор эталона.** Подготовить для конкретного задания `bar.md` с **5–7 проверяемыми механиками**, не расплывчатыми прилагательными. Например, для конкретного пилотного раскрытия автомобиля: не показывать удлинённый силуэт до указанного момента, после хука сделать его однозначно читаемым, зафиксировать ракурс/длительность реакции по утверждённому брифу. Любые численные параметры брать из задания/эталона, не придумывать. Показать bar.md владельцу до запуска.
4. **Петля.** Разбить на **3–4 независимых фрагмента**, если задача это допускает; сборщик делает версию, затем три критика получают **новый изолированный контекст**. Критики имеют двоичный вердикт `PASS/FAIL`, указывают наблюдаемое доказательство и **одну главную дыру** на исправление. **Все три PASS** → фрагмент прошёл независимую проверку; иначе вернуть задачу конкретному сборщику и повторно проверить изменённую версию. Нет фиксированного максимума итераций; но при достижении согласованного денежного/временного предела петля **приостанавливается для решения владельца**, не продолжает тратить деньги сама.

## Два уровня проверки — не смешивать

- **Производственные проверки без полного рендера**: корректность сценарной структуры, соответствие канону, полнота shot list, допустимые параметры модели. Это полезный early QA, но **не финальная ремесленная приёмка** визуального ролика.
- **Финальная приёмка изображения/видео/звука**: критики получают именно результат; для визуального ремесла нужен реально показанный кадр/видеоматериал, для звукового ремесла — прослушиваемая дорожка. Одни текстовые промпты или log сборщика не заменяют результат.

На момент проектирования n8n Agent catalog для Claude указывает входы text/image/pdf; **возможность полноценного просмотра/понимания видео в saved Agent не подтверждена**. Поэтому Codex/FastAPI должен реализовать media-inspection pipeline (стоп-кадры и таймкоды через FFmpeg, фрагменты аудио/расшифровка, сравнения с эталоном). Если этого нет, выводить явный `blocked_missing_render_or_tool`. Не выдавать «прошёл» по одному описанию видео.

## Кто исправляет

Ошибки идут **назад исходному исполнителю**, а не critic сам редактирует артефакт:

- недочёт сцены/юмора → A1 (сценарист);
- визуальная постановка/темп кадра → A2 (режиссёр);
- картинка, референсы, промпт/видео → A3;
- звук, монтаж, выпуск → A5;
- противоречие канона → владельцу и A1 для предложения, **никаких молчаливых правок утверждённого канона**.

A0 фиксирует, какой фрагмент и какая версия возвращены, контролирует зависимости, стоимость и срок, собирает финальный акт приёмки. Повторная проверка должна быть по **новому артефакту**, не по обещанию его исправить.

## Контракт с GremoVOD Web/FastAPI (проектируемый)

Хранить внутри единой базы GremoVOD, а не в отдельном «каноне n8n»:

```json
{
  "review_id": "existing-or-generated-uuid",
  "task_id": "existing-task-id",
  "project_id": "existing-project-id",
  "artifact_id": "selected-artifact-id",
  "artifact_revision": "version-or-content-sha",
  "reference_asset_ids": [],
  "bar_version": "approved-bar-id",
  "round": 1,
  "verdicts": [
    {
      "role": "REVIEW-REQ",
      "result": "PASS",
      "evidence": ["observable evidence"],
      "biggest_gap": null,
      "reviewer_model": "anthropic/claude-haiku-5-5"
    }
  ],
  "status": "reviewing",
  "approval": {"media_render": false, "expert_model": false}
}
```

Значения выше — образец схемы, **не существующие ID или вызовы API**. Все события привязывать к `base_revision`/hash артефакта и версии канона, `git_sha` навыков, выбранной модели и расходам. Форма вердикта для каждого критика: `PASS | FAIL | BLOCKED`, где **BLOCKED не считается PASS**. Подделывать доступ к просмотру результата недопустимо.

Предлагаемые статусы: `intake → preflight → bar_review → building → critiquing → changes_requested → building … → passed_all → awaiting_owner_approval → accepted` и `paused_budget/blocked/cancelled`. `passed_all` означает проверку критиками, а не автоматическое разрешение публикации.

Интерфейс «Петля качества» должен показывать версию артефакта, номер круга, три независимых бинарных результата, одну крупнейшую проблему по каждому FAIL, назначенного исполнителя, историю исправлений, ожидаемую/фактическую стоимость и кнопку остановки/согласования.

## Защита от зацикливания и платежей

- Не запускать Opus и повторные медиа-генерации без **доверенного backend approval**; инструкций A0 недостаточно.
- При достижении согласованного `cost_cap_usd` или при `stop` пользователя — **пауза** до нового подтверждения. Это согласуется с принципом файла «Дизайн-петля» без фиксированного количества кругов.
- Контекст критика: только утверждённые входы/бар/сам артефакт, без builder chain-of-thought, самооценки или предыдущих оценок других критиков; новая модельная сессия каждый раунд.
- Запрет «мягких оценок»: `PASS/FAIL` только с наблюдаемым подтверждением, а не баллом `8/10`. 
- Review на фрагментах делать выборочно в экономном режиме (cheap early checks), финальную тройку — на согласованном видимом результате.
- Skill Sync и изменения в ветке `integration/n8n` не должны автоматически публиковать reviewers.
