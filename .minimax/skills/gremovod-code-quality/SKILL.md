# GremoVOD — гейт качества кода

Обязательный гейт для **любого** изменения программного кода GremoVOD. Каждое правило
ниже закрывает конкретную ошибку, найденную независимой приёмкой PR #58/#62/#63 (пакет
приёмки #65). Правила не заменяют `AGENTS.md`, `CLAUDE.md` и `AGENT_BUILD_MANUAL.md` —
они дополняют их проверкой результата.

Порядок: **1 → 2 → 3 → 4 → 5**. Пропущенный блок означает, что работа не подтверждена.

## 0. Область действия

Гейт обязателен, если изменён хотя бы один файл:

- `backend/**` — Python API, бизнес-логика, миграции SQLite;
- `frontend/**` — React/TypeScript;
- `tools/**`, `scripts/**`, `integrations/**`, `db/**`;
- `.github/workflows/**`, `backend/requirements*.txt`, `frontend/package*.json`.

Гейт не обязателен для правки текстов, `canon/**`, `docs/specs/**` и ответов на вопросы без
изменений в коде. В смешанной задаче гейт обязателен для кодовой части.

## 1. Preflight — до первой строки кода

1. **Состояние репозитория.** `git fetch origin`, `git status --short`,
   `git branch --show-current`, `git worktree list`. База задачи — `origin/mavis/work`
   (актуальный SHA уточняй командой `git rev-parse origin/mavis/work`). **Не работай в
   `main`/`mavis/work` и не в чужом worktree**: своя ветка и свой worktree.
2. **Точка отсчёта.** Если продолжаешь существующий PR, сначала
   `gh pr view <N> --json headRefName,headRefOid,state,isDraft`. HEAD PR дрейфует: в #58
   проверенный SHA `5c47ace` сменился на `c634c0c`, и вердикт по старому SHA не переносится
   на новый. Читай и проверяй **текущий** SHA; любой свой результат привязывай к SHA.
3. **Прочитай затронутый код целиком:** определение функции **и вызывающий код** (callers,
   HTTP-маршруты, `response_model`). Чтение только определения — источник половины находок
   аудита.
4. **Затронутые контракты.** Запрос/ответ, схема таблицы и миграция SQLite, форма ответа
   API, CLI-контракт, тексты workflow. Проверь, что новое поле действительно доходит до
   клиента: фильтр `response_model` режет лишние поля, и «поле есть в БД» ≠ «поле в JSON».
5. **Существующие тесты** по изменяемой области — это база для red → green. Второй набор
   тестов рядом с существующим не заводи.
6. **Сверься с открытыми находками:** комментарии PR, `docs/audits/`, handoff-пакеты. Не
   переделывай уже исправленное и не пропускай уже найденное.
7. **Короткий план** (файлы → меняющиеся сигнатуры → граничные случаи) и **план проверки**:
   какая команда доказывает каждый пункт.
8. **Границы задачи:** что разрешено менять, что запрещено (§6).

## 2. Red → Green — доказательство, а не утверждение

1. **Сначала тест**, воспроизводящий именно эту ошибку.
2. **Покажи падение на старом коде.** Причина падения должна совпадать с дефектом
   (`AssertionError` с верным ожиданием), а не быть `ImportError`, опечаткой или таймаутом.
   Тест, который падает «не по той причине», переписать.
3. **Минимальное исправление** — только то, что чинит дефект.
4. **Покажи зелёный прогон** того же теста.
5. **Не меняй чужие тесты, чтобы стало зелёно.** Если существующий контракт кодифицирует
   сам дефект (пример: `backend/test_money_boundary.py` закреплял «`total_tokens=0`
   освобождает резерв»), смена контракта — отдельное осознанное решение: что меняется и
   почему — фиксируется в отчёте. Молчаливая подмена ожидания прячет дефект.
6. **Без шага 2 исправление не считается подтверждённым.** Если падение доказать нельзя
   (нет окружения, недоступен внешний сервис) — писать «не проверено», а не «исправлено».

## 3. Проверка противоположных сценариев

Для каждого исправления закрывай **релевантные** сценарии: добавлять бессмысленные тесты
ради объёма запрещено, но пропуск существенного — тоже дефект.

| Сценарий | Что проверяем |
|---|---|
| Положительный | штатный путь даёт ожидаемый результат |
| Неправильный вход | `NaN`/`inf`, отрицательные числа, `bool` вместо числа, строки, пустые и огромные значения, malformed JSON или цепочки |
| Отсутствующие данные | `None`, отсутствующий ключ, пустой или неразбираемый ответ провайдера |
| Повторное выполнение | идемпотентность: повторный запуск не снижает подтверждённый факт и не списывает дважды |
| Таймаут и аварийное прерывание | частичная запись откатывается; при неясности списания — `UNKNOWN` и удержание резерва, **повторный submit запрещён** |
| Повторное открытие SQLite | незавершённая миграция (сбой после `ALTER`) докатывается при следующем старте; старые данные не теряются |
| Конкурентный доступ | два процесса не списывают один резерв дважды; гонка не создаёт отрицательный баланс |
| Соседние модули | общий бюджет, ledger и реестр не ломаются; суммы сходятся |

Обязательные частные случаи этого проекта:

- **Противоречивый usage не доказывает отсутствие оплаты.** `total_tokens=0` при
  `prompt_tokens>0`, при `completion_tokens>0`, при отсутствующих обязательных счётчиках или
  при сумме, не равной `prompt+completion` → `submission_unknown`, резерв удерживается,
  причина явная. Один валидатор счётчиков — на всех путях (chat и task).
- **Невалидная цена (`NaN`/`inf`) → `submission_unknown` с причиной, а не `TypeError`.**
- **Недостоверные старые строки не уменьшают бюджет** (отрицательный `usd` из legacy-базы).
- **Malformed-часть нельзя молча удалять:** удаление битого элемента из цепочки сдвигает
  позиции и подменяет identity. Цепочка отвергается целиком.
- **Единый источник правды:** не заводить второй ledger, второй QC-движок или вторую
  систему пользователей.

## 4. CI must be green

1. **Локально, по порядку:** сначала целевые тесты изменённой области, затем проверки,
   относящиеся к области изменения, затем полный регресс, если затронут общий модуль.
   - backend: `python -X utf8 -m unittest discover -s backend -p "test_*.py"`
   - frontend: `npm test`, `npx tsc --noEmit`, `npx vite build`
   - tools и скрипты: их собственные тесты (`python -X utf8 -m unittest tools.test_*`)
2. **После push** дождись GitHub Actions **на точном новом SHA** (`gh run list --commit
   <sha>`). Зелёные джобы прошлого SHA не являются зелёными джобами нового.
3. **Ни одного красного обязательного check → `READY_FOR_CODEX_REVIEW` не пишется.** Любой
   красный check означает, что работа не готова к приёмке.
4. **Проверь, что CI вообще сработал на твои изменения.** Path-фильтры пропускают тяжёлую
   проверку, если изменён сам workflow или сам CI-инструмент. Такой PR не «зелёный», а
   «непроверенный»; docs-only PR честно не выдаёт полную приёмку.
5. **Собственная проверка — не доверенная граница.** Правка проверяющего кода в том же PR
   обходит сам guard. Изменение workflow или guard — отдельное решение владельца, а не
   часть обычной задачи.
6. **Зелёный MOCK не равен приёмке продукта.** MOCK-стенд, изолированная копия данных и
   «юнит-тесты прошли» не заменяют проверку на реальной конфигурации.

## 5. Точность заявлений и handoff

Ошибка аудита была не в коде, а в отчёте: CI-документ называл media-job
информационным, а workflow делал его блокирующим; «487 backend» — это 455 unit + 32 media.

- Каждое утверждение в PR-body или handoff либо **проверено** (с командой и SHA), либо
  помечено как **не проверено**.
- Указывай точные SHA, команды и их фактический вывод: числа тестов, имена джоб,
  идентификаторы прогонов.
- Не переноси результат или вердикт со старого SHA на новый без повторной проверки.
- Перечисляй, что **не выполнялось**: browser E2E, реальный CapCut master, live n8n,
  платные вызовы, backup/restore, работа на реальной SQLite.
- Считай деньги: сколько удержано, сколько подтверждено, что осталось неопределённым.

## 6. Границы — этот гейт не даёт разрешений

- Merge, force-push, auto-merge, изменение настроек репозитория, branch protection и
  списка обязательных checks — только по отдельному решению владельца.
- Платные API и реальные провайдеры — только по отдельному разрешению: конкретный запрос,
  provider, модель, цена, потолок.
- Реальная SQLite, `canon/**`, `docs/specs/**`, чужие worktree и незавершённые правки
  других агентов — не трогать. Миграции проверять на копии.
- `git add -- <точный путь>`, без `git add .` и `git add -A`.
- Коммит и PR — в своей ветке; `main` и `mavis/work` не меняются.

## 7. Чек-лист перед публикацией

- [ ] База, ветка, worktree и `git status` проверены; HEAD PR зафиксирован по SHA.
- [ ] Прочитаны определения **и вызывающий** код; найдены затронутые контракты и тесты.
- [ ] Есть короткий план: файлы, сигнатуры, граничные случаи, команды проверки.
- [ ] Новый тест падал на старом коде **по ожидаемой причине**, после фикса — зелёный.
- [ ] Закрыты релевантные сценарии §3: повторный запуск, таймаут/авария, reopen SQLite,
      конкурентный доступ, влияние на соседние модули.
- [ ] Целевые тесты и проверки области изменения зелёные; полный регресс — если затронут
      общий модуль.
- [ ] После push Actions зелёные **на точном новом SHA**; красных обязательных check нет.
- [ ] Отчёт различает проверенное и непроверенное и перечисляет невыполненное.
- [ ] Границы §6 соблюдены: без merge, без платных вызовов, без правки чужих данных.
